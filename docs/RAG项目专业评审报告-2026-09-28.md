- 评审日期：2026-09-28

- 评审方式：全链路代码走查 + 契约核对 + 与既有 spec/报告交叉验证（未运行测试；结论均标注证据文件:行号）

## 0. 总体结论

**工程成熟度处于「B+ / 生产级骨架已成型」水平，但当前形态不具备上线条件。**

三处 P0 阻塞中，**两处与检索质量无关、纯属入库与配置链路的死结**，且都属于「症状与根因距离远、极易误诊」的类型：

| 级别 | 缺陷 | 一句话 | 证据 |
|---|---|---|---|
| **P0-1** | 双索引标定校验必然 fail-closed | 配 artifact → 默认混合作用域**每次查询都拒答** | `retrieval/service.py:437-453` |
| **P0-2** | 零真实医学语料 | 公共 5 chunk 全为「未经医学审核」样例；私有 7 条是同一 PDF 调试残留 | 记忆 + `docs/知识库搭建评估报告.md` |
| **P0-3** | 复核态无出口 + OCR 置信度不可得 | **扫描件（无文本层 PDF/图片）100% 进复核、永不索引** | `quality/gate.py:327-328`、`per_page_ocr.py:83`、`orchestrator.py:271` |
| **P0-4** | 评估体系多层空转 | 「模拟检索」使 recall/MRR 必然 1.0；RETRIEVE 阶段指标无生产调用点 | `eval/golden.py:524-529`、`observability/stage_metrics.py` |

**P0-3 是本次评审最重要的新发现**，此前未见记录：它意味着系统的核心业务（解读患者检查报告，而报告多为扫描件）在数据入口处就被静默掐断，且表现为「文档上传成功、状态正常、但永远查不到」——与项目最忌讳的「静默失败」模式完全一致。

**最大亮点**：安全与合规设计（ACL 双索引隔离、引用/数值/诊断性结论四重校验、同意与审计、fail-closed 姿态、PHI 明文出网启动拦截）达到**医疗系统的专业水准**，明显高于同类项目基线。P0 缺陷集中在数据与评估链路，而非安全链路。

## 1. 分级问题清单

### 1.1 P0 — 阻断上线，必须修复

#### P0-1｜`CalibrationArtifact` 双索引一致性检查必然失败

- **现象**：配置任何 `CALIBRATION_ARTIFACT_PATH` 后，`LAB_INDICATOR`/`ORDINARY`（默认混合作用域）的**所有查询**返回 0 条 + `calibration_artifact_mismatch`。
- **根因**：`service.py:437-444` 用**单一** `artifact.index_version` 比对 `(*lexical, *vector)` **全部**候选，而两索引版本按设计不同（公共 `public-v1`、私有 `private-v1`）。
- **性质**：既有缺陷，非余弦门禁引入；legacy artifact（仅 `threshold`）同样失败。一直未暴露是因为 `.env` 从未配置该路径。
- **现状**：spec + plan 已完成（`docs/superpowers/{specs,plans}/2026-09-28-per-index-calibration-matching-*`），**待批准编码**。
- **评审意见**：
  1. spec 的技术方案（按 `visibility` 分派、成对必填、旧 artifact 行为逐字节不变）**正确且克制**，同意 §7.2「不自动放宽」的决策（隐式语义变更是更坏的失败模式）。
  2. §4.4 选 `record.visibility` 而非 `index_name` 判定归属，理由充分（`visibility` 是协议字段且已被 `_record_from_hit` 强校验），但**应补一条防御**：`visibility` 与 `index_name` 的交叉校验目前只在 `OpenSearchStore` 内做，自定义 `SearchIndex` 实现可能不一致。
  3. §8 I9 是真正的验收核心（"能启用"必须由"门禁确实在工作"证明），同意。
  4. **补充要求**：修复后必须补一条「混合作用域 + artifact + 双索引」的**真实链路**测试；三个已知空洞（单测假索引两路同源、wiring 只断言构造期属性、验收脚本直传参数绕过 artifact）必须在同一 PR 内闭合，否则同类缺陷会再次潜伏。

#### P0-2｜知识库无真实医学语料

- **现状**：公共库 5 chunk 全来自 `knowledge/samples/hypertension-sample.md`（文件自述"未经医学审核，不得发布"）；私有库 7 条为同一份 `blood_report.pdf` 反复上传的调试残留。私有源 PDF 无中文字形（仅 Helvetica + ZapfDingbats，无 ToUnicode 表）。
- **影响**：所有排序指标（recall/MRR/nDCG）、阈值标定（`cosine_threshold=0.50`）、门禁参数都建立在 12 条语料上，**不具备统计意义**；`candidate_limit`/`rerank_limit` 实测「测不出差异」正是语料过小的直接后果。
- **评审意见**：
  - 语料是**一切调优的前置条件**，优先级应高于任何检索参数优化。
  - 建议路径（按性价比排序）：① 人工下载 3-5 份官方指南（如《中国高血压防治指南》《成人血脂异常防治指南》）→ `knowledge-ingest` CLI；② 构造一份**含负样本**（无关文档）的语料集，否则门禁的拒答能力永远无法验证；③ 语料规模上到 500+ chunk 后重标定 `cosine_threshold` 与 `candidate_limit`。
  - **不要**为了「有数据」而灌入未审核内容——当前样例文件的自我声明已表明这是合规红线。

#### P0-3｜复核态无人工出口 + OCR 置信度不可得 → 扫描件永不入库（新发现）

- **事实链**：
  1. `per_page_ocr.py:61,83`：`PerPageOCRBackend.recognize_page` **只返回文本行、不返回置信度**，因此 OCR 产出的 `EvidenceUnit.confidence=None`（这是**诚实**的设计，不伪造 0.95）。
  2. `gate.py:208-222`：`_confidence_unavailable_ratio` 统计「有内容但 `confidence is None`」的单元占比。
  3. `gate.py:327-328`：只要该比值 `> 0.0` → 追加 `REASON_CONFIDENCE_UNAVAILABLE` → 落入 `NEEDS_REVIEW` 分支（`gate.py:349-352`）→ **`retrieval_eligible=False`**。
  4. `orchestrator.py:271`：公共记录构造**硬编码** `retrieval_eligible=True`，与证据实体的 `retrieval_eligible` **完全脱节**。
  5. `orchestrator.py:253-254`：`if not eligible: raise RuntimeError` — 仅校验文档/版本状态，**不读 `evidence.retrieval_eligible`**。
  6. 全库 grep `review|approve|复核通过|manual_review`：**没有任何「人工复核通过」的状态迁移路径**（仅测试覆盖率叙事、`parsing/service.py:864` 的 review 标记事件）。
- **后果（两条独立的死结）**：
  - **扫描件（临床上绝大多数检查报告）**：无文本层 → 走 OCR → 置信度不可得 → 必然 `NEEDS_REVIEW` → `retrieval_eligible=False` → **永远不可检索**。而文档状态接口仍显示「上传成功、NEEDS_REVIEW」，患者侧表现为「查不到任何东西」。
  - **即便将来接上修复，公共路径**：`_public_record` 硬编码 `retrieval_eligible=True`，会让 `retrieval_eligible=False` 的证据**绕过质量门禁重新变为可检索**——这是一条**安全语义倒挂**路径。
- **评审意见**：
  - 必须在 spec 阶段明确「OCR 缺失置信度」的**正确处置**：合理解是「用其他信号替代」（如异常字符比例、字典命中率、行均长度方差），而不是把「不可判定」直接等同「不合格」；`gate.py:197-201` 的注释已经正确识别了「不可判定 ≠ 低置信度」，但**结论方向反了**——它是「按不可判定报」，而不是「按不可判定放行」。
  - 必须实现人工复核出口（review 状态迁移 + 审计 + 谁可放行、放行后 `retrieval_eligible` 如何翻转），否则 `NEEDS_REVIEW` 就是一个**只进不出的黑洞**。
  - 修复 `_public_record` 的 `retrieval_eligible` 硬编码，使其与 `EvidenceUnit.retrieval_eligible`（及版本状态）**取交集**。

#### P0-4｜评估体系多层空转，「指标全绿」不可作为验收依据

- **事实链**（均由并行扫描确证）：
  - `eval/golden.py:524-529`：`_rag_metrics_for_fixture` 用「模拟检索」——`produced` 就是分块产物自身，`returned = list(dict.fromkeys(produced))`，K == 产出数；空 `gold_anchors` 时 `recall, mrr, permission, deletion = 1.0, 1.0, 0, 0`。**recall/MRR 必然 1.0**。
  - `tests/eval/` 下**没有任何**测试调用 `RetrievalService.retrieve`；`grep .retrieve(` 仅出现在 `unit/`、`integration/`。
  - `observability/stage_metrics.py` 提供 `PipelineStage.RETRIEVE` 与 p95 桶，但 **`src/` 内无任何文件 import 它**；`record_retrieve` 无生产调用点 → **检索阶段指标在生产不可见**。
  - `tests/integration/test_live_opensearch.py` 默认 `pytest.skip`（需 `RAG_LIVE_OPENSEARCH=1`），唯一真实 OpenSearch 链路不在 CI 默认执行。
- **后果**：CI 绿灯与「检索质量」之间**没有因果关系**。发布门控（`release_gate`）比较的是自评指标，且 `baseline is None` 时「金标准集自身即定义基线并通过」（`golden.py:737-740`），首次运行必然通过。
- **评审意见**：
  - 保留 `golden.py` 作为**文档质量**评估（它确实在做分块/锚点/表格的质量校验，且锚点推导是 fail-closed 的，这部分设计优秀），但必须**从检索质量口径中剥离**。
  - 新建真实检索评估：真实 OpenSearch + 真实 `RetrievalService.retrieve` + 显式 `k=top_k` + **`content_hash` 去重口径**（私有库有 4 条文本相同记录，按索引 ID 算召回会虚高）。
  - 把 `stage_metrics` 的 RETRIEVE 接入 `service.py`，否则 P95 目标（当前报告 131ms）无法被持续监控。
