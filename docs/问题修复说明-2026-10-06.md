# 医疗 RAG 项目问题修复说明

**日期：** 2026-10-06  
**依据：** 当前代码走查、前端构建与测试、部署配置检查  
**适用范围：** `src/medical_rag`、`frontend`、Docker Compose、CI 与运行配置

## 1. 结论

当前项目具备较完整的 RAG、权限、引用和质量门禁骨架，但仍存在上线阻断问题。修复应按以下顺序推进：

1. 医疗安全与患者数据隔离；
2. OCR 复核闭环与检索资格一致性；
3. 异步解析、向量化和索引发布链路；
4. 真实检索评估和生产可观测性；
5. 部署、凭据和工程治理收口。

本说明是修复计划和验收依据；当前实施状态见第 7 节，真实基础设施 E2E 仍需在部署环境验收。

## 7. 本轮实施结果

已完成 P0-1 至 P0-4：急症识别优先级、前端登出清理、明文 PHI 出口门禁，以及 OCR 质量门禁与人工复核闭环。人工复核现由 `DocumentReviewService` 统一处理角色校验、原因精确确认、`NEEDS_REVIEW -> READY` 状态迁移、IndexJob 重置/创建和审计记录；复核接口为 `POST /v1/documents/{document_id}/review`。

已完成 P1-1 至 P1-5 的代码收口：Compose worker/索引初始化、上传扫描与请求体上限、公共索引事务补偿、多租户登录冲突和停用账号校验、真实检索评估接缝与 retrieve 指标记录。

验证方面，前端 Vitest 4 个文件 28 个测试通过，前端生产构建通过，Python 源码与 worker 脚本通过 `compileall`，Compose 配置在补齐占位凭据后通过。当前环境没有后端 pytest/ruff 依赖，因此后端集成测试和 lint 尚未执行；真实 ClamAV、OpenSearch、Celery 和远程模型链路仍需在部署环境完成 E2E 验收。`.env` 中已有的真实或疑似真实凭据仍需由部署方轮换。

## 2. P0 修复项

### P0-1 急症识别漏报

**问题**

`SafetyService` 将“正常吗”“会不会得”等一般问询信号作为急症豁免条件。类似“我胸痛正常吗”“我呼吸困难正常吗”的第一人称短句可能被放行到检索和模型回答，绕过急诊提示。

**代码位置**

- `src/medical_rag/safety/service.py:27-34`
- `src/medical_rag/safety/utterance.py:66-96`

**修复要求**

- 第一人称急症症状优先级高于一般知识问询；
- 只有明确的第三人称、转述或科普语境才能豁免急症升级；
- 增加中文、英文和否定/转述语境的回归测试；
- 急症命中后不得调用检索、重写或模型。

**验收标准**

| 输入 | 期望结果 |
|---|---|
| `我胸痛正常吗` | `URGENT_ESCALATION` |
| `我呼吸困难正常吗` | `URGENT_ESCALATION` |
| `网上看到有人说胸痛怎么回事` | 不升级，可进入科普路径 |
| `我今天胸口疼喘不上气` | `URGENT_ESCALATION` |

### P0-2 跨账号会话和报告状态泄露

**问题**

退出登录只清除 JWT，未清理 Chat/Document Pinia 状态和会话 `localStorage`。同一浏览器切换账号时，旧用户的消息、会话 ID 或报告列表可能继续显示。

**代码位置**

- `frontend/src/App.vue:63-66`
- `frontend/src/stores/auth.ts:30-33`
- `frontend/src/stores/chat.ts:23-55`
- `frontend/src/stores/documents.ts:6-15`

**修复要求**

- 登出时统一执行 `chat.reset()`、`documents.clear()` 和会话存储清理；
- 按租户/患者隔离本地持久化键，禁止跨身份复用 session ID；
- 登录成功后清理上一个身份的内存态，再加载当前身份数据；
- 增加“用户 A 登出 → 用户 B 登录”的端到端回归测试。

**验收标准**

- 用户 B 登录后看不到用户 A 的消息、报告、会话 ID 或上传状态；
- 清空本地存储后不会恢复其他身份的会话；
- 后端仍必须继续执行会话和文档归属校验。

### P0-3 患者数据明文外发和凭据轮换

**问题**

当前 `.env` 使用远程 HTTP 模型/OCR 地址，而开发环境允许该配置通过。医疗报告和问题可能经公网明文发送；本地配置还包含模型网关、OCR、对象存储等敏感凭据。

**代码位置**

- `src/medical_rag/core/config.py:47-53`
- `src/medical_rag/core/config.py:204-218`
- `.env` 中的模型网关、对象存储和 OCR 凭据

**修复要求**

- 立即轮换当前 `.env` 中所有真实凭据；
- 默认模型网关改为空值或仅允许 loopback/mock；
- 所有承载 PHI 的远程地址必须使用 HTTPS；
- 生产、预发布和共享测试环境统一 fail-closed；
- 禁止把真实凭据写入仓库、日志、诊断信息和文档。

**验收标准**

- 非回环 HTTP 的模型、OCR、OpenSearch、对象存储地址在启动时被拒绝；
- `.env.example` 不包含真实地址、用户名或凭据；
- 凭据扫描和 CI secret 检查通过。

### P0-4 OCR 复核黑洞与资格倒挂

**问题**

OCR 后端不提供置信度时，质量门禁把文档置为 `NEEDS_REVIEW` 和 `retrieval_eligible=False`，但系统没有人工复核通过接口。与此同时，公共索引构造路径允许 `NEEDS_REVIEW` 并硬编码 `retrieval_eligible=True`，存在绕过门禁的风险。

**代码位置**

- `src/medical_rag/parsing/per_page_ocr.py:61-84`
- `src/medical_rag/quality/gate.py:325-352`
- `src/medical_rag/indexing/orchestrator.py:245-271`
- `src/medical_rag/api/routes/documents.py:54-191`

**修复要求**

- 为 OCR 缺失置信度增加替代质量信号；
- 实现带角色鉴权和审计的 `NEEDS_REVIEW -> READY` 复核流程；
- 复核通过必须重新评估、翻转 `retrieval_eligible` 并创建索引任务；
- 复核失败或索引失败时整体回滚；
- 公共和私有路径统一执行 `PASS/READY -> eligible=True`、`NEEDS_REVIEW/FAIL -> eligible=False`；
- 全扫描 PDF 在仅配置 `per_page_ocr` 时直接走逐页 OCR，不得调用空的整文档 OCR 接口。

**验收标准**

- 正常 OCR 文本可以进入 `READY` 和索引；
- 垃圾 OCR 保持 `NEEDS_REVIEW` 且不可检索；
- 复核通过后可检索，并产生审计事件；
- 索引写入失败时状态仍保持 `NEEDS_REVIEW`；
- 全扫描 PDF、混合 PDF、缺页 PDF 均有回归测试。

## 3. P1 修复项

### P1-1 Compose 缺少 worker，且 embedding/analyzer 配置不一致

`docker-compose.yml` 没有 Celery worker。上传会发布 `medical_rag.parse_document`，但没有消费者处理任务。同时 API 容器没有传递 `EMBEDDING_BACKEND`、`EMBEDDING_DIMENSIONS`、本地模型路径和 `RAG_*` analyzer 配置，默认值与当前本地运行环境不一致。

**修复要求**

- 增加独立 worker 服务和健康检查；
- 增加索引初始化/迁移步骤；
- API、worker 使用同一份 embedding、维度、index version 和 analyzer 配置；
- OpenSearch 未安装 `analysis-ik` 时显式使用 `cjk` 或安装插件；
- 增加“上传 → 解析 → 向量化 → 入索引 → 查询”的 Compose E2E。

### P1-2 上传缺少真实病毒扫描和请求体上限

`UploadService` 默认使用 `AllowAllVirusScanner`。前端的 50 MiB 限制不能防止直接调用 API；Nginx 未设置 `client_max_body_size`，超大 multipart 可能先消耗磁盘和 IO，之后才被应用拒绝。

**修复要求**

- 生产环境没有真实扫描器时拒绝启动或进入隔离队列；
- Nginx、ASGI 和服务层统一限制请求体；
- 对 chunked/no `Content-Length` 请求执行流式限额；
- 病毒扫描结果、失败原因和重试状态写入审计。

### P1-3 数据库与索引发布不是原子流程

公共知识更新会先停用旧 chunk，再执行 embedding 和 OpenSearch upsert。中途失败时数据库事务可能回滚，而索引已经部分更新，造成旧内容继续可检索或新内容缺失。

**修复要求**

- 用 outbox 事件作为数据库提交与索引发布之间的可靠边界；
- 索引写入必须幂等，可重试并可补偿；
- 失败时生成残留指标和告警；
- 增加“部分 upsert + 数据库回滚”测试。

### P1-4 账号状态和多租户登录约束

JWT 校验只检查患者存在及租户一致，没有检查患者是否仍为 `ACTIVE`。登录查询只按手机号查询，而数据库唯一性是 `(tenant_id, external_user_id)`，同手机号跨租户时可能抛 500。

**修复要求**

- token 校验增加 `Patient.status == ACTIVE`；
- 登录增加租户上下文，或建立明确的全局唯一身份标识；
- 冲突身份返回稳定的 401/400，不得泄露租户信息或返回 500；
- 增加停用账号和跨租户同手机号测试。

### P1-5 真实检索评估和生产指标缺失

Golden 评估器用生成出的 chunk 模拟检索，`recall/MRR` 不能代表真实 OpenSearch 质量；`PipelineStage.RETRIEVE` 在生产代码中没有 recorder 调用点。

**修复要求**

- 使用真实 `RetrievalService.retrieve` 和真实索引执行评估；
- 固定 `top_k`、去重口径、权限负样本和删除残留样本；
- 在 retriever/orchestrator 接入统一 recorder；
- 导出检索延迟、拒答率、门禁跳过、embedding 降级和权限违规指标。

## 4. P2 工程改进

- 通过反代时读取真实客户端 IP，避免登录限流全部落到 Nginx 地址；
- CI 增加前端 build/test、依赖漏洞扫描、镜像扫描和 Compose E2E；
- 为 Python/npm/Docker 固定版本或生成 lock/hash；
- 缩小前端首包，当前生产 JS 约 1.08 MB；
- 为登录成功、失败、限流和账号停用补充审计事件；
- 修复 Git 仓库损坏，恢复可审计的提交基线。

## 6. 推荐发布门槛

完成以下条件后才进入灰度：

1. P0 全部关闭，并通过安全回归测试；
2. Compose 中 API、worker、数据库、Redis、MinIO、OpenSearch 全部可启动；
3. 至少一条真实扫描件完成“上传—复核—索引—检索—引用”闭环；
4. 真实检索评估集包含正样本、负样本、删除样本和跨患者权限样本；
5. 后端 pytest/ruff、前端测试、镜像和依赖扫描在 CI 中稳定通过；
6. 凭据完成轮换，所有 PHI 出网链路使用 HTTPS；
7. Git 仓库恢复后重新建立可追溯的发布标签和回滚点。
