## 1. 结论摘要

**总体判断：知识库的工程化实现达到生产级水准，但作为"知识库"尚未真正投入运营。**

三个层面需要分开评价：

| 层面 | 评价 | 依据 |
|---|---|---|
| **工程质量** | 优秀 | 639 项测试全绿；fail-closed 贯穿全链路；公共/私有物理隔离；幂等写入与对账补偿完备 |

## 3. 分维度评估

### 3.1 解析与清洗 —— 良好（4/5）

**做得好：**

- **五类格式全覆盖**：PDF（`PdfTextParser`）、DOCX（`WordTextParser`）、XLSX/XLS（`ExcelParser`）、图片（`ImageOCRParser`）。
- **Excel 处理深度超出一般水平**：`_SheetGrid` + `_detect_header_index` 处理**多级/合并表头**，`_format_spreadsheet_cell` 还原日期/数字格式，`table_cell_range` 产出精确 `A1:B26` 型锚点。
- **OCR 回退策略严谨**：`should_ocr_page` 逐页判定；全缺文本 → 整份 OCR；混合页 → 逐页补扫并保留页身份；**无法确认页数时抛 `MixedPdfOcrDeferredError` 而非静默假设覆盖**。这是典型的"宁可不做，不可做错"。
- **清洗器契约清晰**：`DocumentCleaner` 只做原地归一化（NFKC、不可见字符、OCR 断行合并、模板行检测），保证 raw↔clean 一一对应，`raw_text` 永不覆盖。

**边界与不足：**

- **仓库无 PDF→图像渲染器**（无 pypdfium2/pymupdf/pdf2image），逐页 OCR 后端 `per_page_ocr.py` 基于确定性 fixture transport。真实生产环境的逐页 OCR 需替换为真实渲染器——调用方接口已预留，但**能力本身尚未落地**。
- 非 PDF 文件无权威页数来源，`_with_page_total` 退回块页码最大值，缺页判定在非 PDF 上不可用。

### 3.2 分块策略 —— 良好（4/5）

**做得好：**

- **语义边界感知**：标题块作为边界且**永不进入 chunk 文本**（其信息保存在 `section_path`）；表格块作为材料边界切断 overlap。
- **表格分块有真实工程考量**：表头在**每个子块中重复**，`cell_range` 描述数据主区间，且行长 × 行数超 `max_tokens` 时提前收口——避免了"表头丢失"和"超出模型窗口"两类常见故障。
- **token 预算自洽**：`HeuristicTokenCounter` 按字符脚本自适应折算（汉字 ≈1.5 字符/token，拉丁 ≈4），修正了单一常量对英文高估约 2.7 倍的问题。
- **overlap 计入预算**：`_bounded_overlap_prefix` 把前缀收缩到 `count(prefix + text) <= max_tokens`，修掉了旧实现"硬上限名不副实"的缺陷。
- **硬切可观测**：`hard_split` flag 会被 `QualityGate` 捕获并触发人工复核（`max_hard_split_ratio = 0.0`，任何硬切都需复核）。

**取舍与不足：**

- **按页/sheet 分组切分切断跨页语义**：`_chunk_cleaned` 为保证页级溯源，把文档切成互不跨 `(page_number, sheet_name)` 的视图再分块。代价是**跨页延续的段落无法合并**，长文档的语义连贯性受损。这是"溯源精度 vs 语义完整"的显式权衡，选择是合理的，但需知悉。
- **父子层级覆盖有限**：`parent_block_id` 仅在**表格子块**（`semantic_chunker.py:322/342`）和**超长块切分**（`:253`）时赋值；普通累积块为 `None`（`:236`）。因此 Task 9 的上下文扩展**只对表格和超长段落生效**，占多数的普通段落走 pass-through 不扩展。扩展能力的实际覆盖面比文档描述的要窄。
- `min_tokens` 在默认配置（`min_tokens=80 ≤ target_tokens=400`）下**天然失效**——docstring 已诚实说明，但这意味着该参数是"死参数"，易误配。

### 3.3 质量门与可观测 —— 优秀（5/5）

这是整个系统最扎实的部分之一。

- **单一阈值来源**：所有阈值集中在 `QualityPolicy`（`quality/gate.py:50`），无散落字面量。11 项指标全部返回供观测。
- **判定语义严谨**：
  - `PASS` → READY，允许 SEARCHABLE IndexJob
  - `NEEDS_REVIEW` → 内容保留但 `retrieval_eligible=False`（write-but-flag）
  - `FAIL` → 内容保留、稳定错误码 `quality_fail:<reason>`、保留源文件供重处理
- **"不可判定" ≠ "低置信度"**：`confidence_unavailable_ratio > 0` 时报 `confidence_unavailable`，**不再**用占位 0.0 去报 `low_ocr_confidence`。这个区分在医疗场景很重要，很多实现会混淆。
- **指标口径经过修正**：`_text_coverage` 从"raw↔clean 字符比"（恒 ≈1 的空转指标）改为"原始块非空白字符 → 最终证据文本非空白字符"的端到端口径，且分母排除 heading 块避免误报。
- **页覆盖 fail-closed**：`page_total is None` 时返回 1.0 且**不判定缺页**（不假定已覆盖）；页码越界证据既不计入覆盖，也不允许虚报。
- **运维闭环完备**：`IndexOrchestrator._dead_letter` 让 `PERMANENT_FAILED` 成为可告警的持久状态（而非静默终态）；`reconciliation.py` 提供隐私安全的 DB/索引对账与确定性修复；`stage_metrics.py` 提供分阶段耗时。

### 3.4 索引与写入 —— 优秀（5/5）

- **公共/私有物理隔离**：两个独立物理索引 + 独立 writer 实例，writer 构造时强制校验 `visibility`，公共 writer **拒绝** ACL 字段，私有 writer **要求** ACL 字段。
- **mapping 完整且前瞻**：`ensure_mapping` 显式声明 `parent_block_id`、`chunk_index`、`section_path` 等——注释明确指出"未声明的字段会被动态映射为 text，导致排序/过滤不可靠"。这类细节通常被忽略。
- **中文检索正确性**：默认 `ik_max_word` / `ik_smart`，并显式要求"回退必须显式配置，不允许静默降级"（`cjk` 为内置回退）。
- **幂等写入**：`doc_as_upsert` 用 update 动作（注释记录了在 OpenSearch 2.18 上把 `doc_as_upsert` 放进 action metadata 会被拒绝的实测结论）；`_idempotency` 键由"文档版本 + 证据 + parser/cleaner/chunker/extractor/embedding/index 全指纹"构成。
- **失败不静默**：`OpenSearchWriteError` 携带 `WriteReceipt`（attempted/succeeded/failed），批量写入部分失败会抛错而非静默丢弃。
- **删除补偿**：删除先写 DB tombstone，再清理对象存储/派生数据/私有索引；`IndexWorker` 检测到文档已删除时**物理删除私有索引**而非写入墓碑，避免延迟任务复活已删数据。

### 3.5 检索与融合 —— 优秀（5/5）

- **权限先行**：`_is_authorized` 在融合与重排**之前**执行，含 `deleted / source_active / retrieval_eligible` 三项生命周期校验 + tenant/patient 双校验。
- **来源绑定 fail-closed**：`_record_from_hit` 校验 `_index` 与 visibility 一致性，且"显式 eligible 但无来源"的命中直接丢弃。
- **降级语义正确**：`_empty_reason` 严格区分 `retrieval_unavailable`（集群/服务故障）与 `insufficient_evidence`（医学证据不足）——**绝不会把服务故障呈现为"没有足够医学证据"**。
- **门禁显式化**：`GatePolicy` 四态（CALIBRATED / EXPLICIT_THRESHOLD / RANK_GATE / TOP_K）替代了原先的 0.5 魔数默认值。原实现会把单路 rank≥2 的候选全部砍掉（归一化上界恰为 0.5），使 `top_k=8` 只回 1-2 条——这个 bug 已修复且注释完整记录了成因。
- **校准一致性校验**：`CalibrationArtifact` 与 RRF 参数、embedding 模型、阈值不匹配时启动即抛错；候选记录的 `index_version` / `embedding_model` 与 artifact 不一致时 fail closed 返回空。

### 3.6 医学事实抽取 —— 薄弱（2/5）

`RuleBasedMedicalFactExtractor`（`parsing/service.py:85`）的 `_patterns` **只定义了一个正则**，仅匹配"血红蛋白 / Hemoglobin"，`_allowed_units` 也只有这一项。

- 对医疗知识库而言，事实抽取的覆盖面**极窄**，无法支撑"指标趋势""异常项识别"等患者端高频需求。
- 缓解因素：`QualityPolicy.min_fact_coverage = 0.0`，事实抽取被定位为**可选**，不阻断入库；抽取器接口 `MedicalFactExtractor` 可替换为治理过的适配器。
- 但需注意：`MedicalFact` 表、`reference_low/high`、`abnormal_flag`、`canonical_name`、`unit_normalized` 等字段已完整建模，**数据结构先行、抽取能力滞后**。

### 3.7 评测体系 —— 框架完整，但存在自证问题（2/5）

**框架层面做得好：**

- Fixture schema 强校验（缺字段**报错而非静默通过**）；`expected_anchors` 由几何信息（bbox / sheet+range / page）**派生**而非字面量复制，刻意打破"从源复制"的同义反复。
- `release_gate` 拿**已存储的 baseline** 与**新鲜运行**对比（而非自比自），P95 容忍 3× 抖动以避开时钟噪声，安全项非零则无条件失败。
- FAIL 时**不覆写** `baseline.json`，避免用更差的数值污染参考基线。

**但关键缺陷在于数据的真实性：**

1. **评测集全部为合成 fixture**，`tests/golden/README.md` 明确声明"fictional, medically plausible content only"，无任何真实脱敏语料。
2. **检索指标是构造出来的**。`_rag_metrics_for_fixture`（`eval/golden.py:518`）注释原文：

   > "Simulated retrieval: produced chunks ranked in reading order (all of them), so K == len(produced)."

   即：把所有产出块按阅读顺序全部返回当作检索结果，于是 `chunk_recall_at_k = 1.0`、`mrr = 1.0` 是**数学上必然**的结果，**不反映任何真实检索质量**。当前 `baseline.json` 全 1.0 / 全 0 正是这一构造的产物。
3. **解析器被旁路**。README 的 "Known limitation" 章节自己承认：fixture 直接注入 `ParsedBlock`，因此 `adapters.py` 的真实解析器、OCR 分支、`FLAG_OCR_NOISE_CHECKED`、逐页 OCR 回退**都未被评测覆盖**；产出的 chunk `parser_version=None`，parser 版本溯源也无法验证。

**结论**：评测**框架**是资产（值得保留），评测**数据**尚未建立。目前的 1.0 分数不能作为任何上线依据。

### 3.8 运营入口 —— 缺失（1/5）

这是**最需要立即处理的问题**。

全仓库检索 `KnowledgeIngestService` / `KnowledgeSourceRegistry` 的调用点，结果**只有测试文件**：

```
tests/integration/test_knowledge_ingest.py
tests/integration/test_index_reconciliation.py
```

生产侧入口核查结果：

| 入口类型 | 现状 |
|---|---|
| API 路由 | `api/routes/` 仅 `auth.py`（consent）、`chat.py`、`documents.py`（患者报告）。**无 knowledge/admin 路由** |
| CLI | `cli.py` 仅 `create_patient`、`evaluate_document_quality` 两个命令。**无知识源注册/入库命令** |
| 前端 | `frontend/src/views/` 仅 `ChatPage`、`ConsentPage`、`DocumentsPage`、`LoginPage`。`DocumentsPage` 标题为"我的报告"，**无知识库管理界面** |
| 运维脚本 | `scripts/run_worker.py` 提供 `init-indexes`（建索引/别名）与 `worker`（解析消费），但**不涉及公共知识入库** |

**影响**：目前要把一份公共医学知识录入知识库，只能**编写 Python 代码直接调用** `KnowledgeSourceRegistry.register()` + `KnowledgeIngestService.ingest()`。这意味着：

- 无法由医学审核人员在界面上完成"登记 → 上传 → 审核 → 启用"闭环；
- 无法运维性地批量导入现有医学知识资产；
- 公共索引在当前部署下**极可能是空的**——而检索链路的公共分支设计得再完善，没有数据也返回不了证据。

**这是"知识库"与"知识库系统"之间的差距所在。**

## 5. 整改建议（按优先级）

### 第一步：让知识库有数据（P0）

1. **补齐公共知识运营入口**，三选一或组合：
   - **CLI 命令**（成本最低）：`python -m medical_rag.cli register-source` / `ingest-knowledge`，复用 `KnowledgeSourceRegistry` + `KnowledgeIngestService`；

2. **导入第一批真实脱敏语料**：建议从检验项目释义、常见指标参考范围、药品说明书入手（结构化程度高、风险可控），目标 200-500 份。
3. **重建评测集**：
   - 保留现有合成 fixture 作为**解析/分块回归测试**；
   - 新增**真实脱敏语料上的检索评测集**，标注 `(question, gold_evidence_ids, forbidden_ids, deleted_ids)`；

   - 在真实评测集上跑出**真正的 baseline**，再启用 `release_gate` 的严格模式。

### 第二步：补齐能力短板（P1）

4. **扩展事实抽取**：至少覆盖血常规、生化、尿常规的常见项目（20-50 个指标），并接入 `default_measurement_names()` 的环境变量注入机制。

6. **扩展父子块策略**：为普通段落也建立父子关系（如按 section 或固定窗口分组），让上下文扩展覆盖全量证据。

### 第三步：固化与治理（P2）

10. 生成并审核 `CalibrationArtifact`，把门禁从 `TOP_K` 升级到 `CALIBRATED`。
11. 清理 `min_tokens` 死参数（或改为在 `min_tokens > target_tokens` 时告警）。
