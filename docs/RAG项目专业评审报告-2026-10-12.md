## 一、P0 问题（上线阻塞 / 安全事故级）

### P0-1 交付完整性事故：git 对象库损坏 + src/tests/frontend 源码全部丢失
- **证据**：`git log`/`git status`/`git show :<file>` 全部 `fatal: bad object HEAD`（对象库丢失，索引成孤本清单）；git 索引含 96 个 `src/` 文件、84 个 `tests/` 文件，但磁盘上均不存在；`frontend/` 只剩 `dist/` 构建产物，`frontend/src` 丢失。
- **影响**：Dockerfile `COPY src ./src` 失败 → 项目**当前不可构建、不可测试、不可运行**；639 项测试无法回归；后端唯一副本是 i18n 工具留下的 `.i18n_backup_src_medical_rag/`（目录名与 `medical_rag` 包名对不上，import 路径无法解析）。
- **建议**：从原始开发机重新打包恢复 `src/`+`tests/`+`.git`；应急可将 `.i18n_backup_src_medical_rag` 重命名回 `src/medical_rag` 作为恢复起点；**以后不要再通过微信传输目录交付项目**。

### P0-2 真实凭据泄漏 + 含 PHI 的数据库随目录外发
- **证据**：`RAG/.env` 含真实 `MODEL_GATEWAY_API_KEY`（且指向公网 `http://121.40.34.96:18097`）、`OCR_PASSWORD=12345678`（弱口令）；`medical_rag.db`（630KB，含聊天/患者/consent 表）、`medical_rag.db.bak`、`backups/` 内数据库与私有索引备份均在目录内。`.env` 虽未入 git，但**本项目目录正是经微信分发的**，等效于凭据与 PHI 泄漏。
- **影响**：任何拿到目录的人可盗用网关 key（可外发数据）、可横向利用弱口令；患者数据外泄属合规事故级。
- **建议**：立即轮换 `MODEL_GATEWAY_API_KEY`、修改 OCR 口令；对 db 文件做脱敏或删除；给 `.env`、`*.db`、`backups/` 加 `.gitignore`（部分已加但未阻止分发）。

### P0-3 PHI 明文出公网
- **证据**：`.env:14-18` `ALLOW_PLAINTEXT_PHI_EGRESS=true` 且 `MODEL_GATEWAY_URL=http://121.40.34.96:18097/v1`——患者问句（PHI）经明文 HTTP 出公网。机制设计本身是对的（`validate_runtime` 会在非 dev 环境拒绝启动），但当前配置事实上让医疗问答明文出网。
- **建议**：本地联调改用回环 sidecar（`.env.example` 的 `127.0.0.1:18097` 方案）或给网关上 TLS。

### P0-4 检索拒答门禁"文档已验收、代码不存在"
- **证据**：
  - 生产组装根默认不配 `CALIBRATION_ARTIFACT_PATH` → `GatePolicy.TOP_K`（即零门禁）（`api/composition.py:105-118`）；
  - 全库 grep `cosine` 零命中——调参报告 §3.3/§4 声称的「vector_score 余弦绝对阈值 0.50→0.52」修复**一行都不存在**，`vector_score` 只进 diagnostics（`retrieval/service.py:410`）；
  - `CalibrationArtifact`（`observability/metrics.py:151-181`）没有报告声称的成对 `index_version`、`score_space`、`cosine_threshold` 字段；
  - 实测报告自证：out-of-scope 查询返回 `cal=0.99~1.0` 满额 top_k、从不拒答。
- **影响**：这是项目已知的核心生产缺陷，现状依旧。评测集里 30 条拒答用例因此**不构成回归门禁**——评测体系自己都测不出"门禁修没修好"。
- **建议**：以代码而非报告为验收基准重新立项该缺陷，一次做全四件事：① vector_score 绝对阈值门禁 ② CalibrationArtifact 成对 index_version + score_space 标注 ③ 向量降级时跳过门禁（否则单路 RRF 上限 0.5 < 阈值 0.52，embedding 一抖动就全量拒答）④ 与 RRF 融合的衔接。

### P0-5 上传链路无审计（PHI 摄取无痕迹）
- **证据**：`ingest/upload_service.py:76-130` 全程无 `AuditService.record`；`AuditAction` 枚举中无 upload 相关动作。对比：下载有 `DOCUMENT_ACCESSED`、删除有 `DELETION_REQUESTED/COMPLETED`。
- **影响**："谁在何时上传了谁的病历"无法回答，合规审计闭环最大缺口。
- **建议**：新增 `AuditAction.DOCUMENT_UPLOADED` 并在 `create_document` 落审计。

### P0-6 配置键静默失效
- **证据**：`.env` 记录的 `ALLOW_PLAINTEXT_PHI_EGRESS` 及语义，在 `core/config.py` 中无对应字段，且 `Settings.model_config` 设了 `extra="ignore"`（config.py:35）——键被**静默丢弃**。
- **影响**：文档-代码漂移；`extra="ignore"` 会让未来所有键名拼写错误静默失效，对安全相关配置尤其危险。
- **建议**：对齐实现与文档；`extra` 改 `forbid` 或对未知安全相关键告警。

## 三、P2 问题（择要）

1. **登录限流为进程内存态**，多副本失效（`auth/throttle.py` 自认）；迁 Redis。
2. **api 服务 8000 端口绑 `0.0.0.0`**，与 postgres/opensearch 等全绑 127.0.0.1 的策略自相矛盾；改 `"127.0.0.1:8000:8000"`。
3. **迁移链根本缺陷**：0001 用 `Base.metadata.create_all` 建全量 schema 而非冻结历史 DDL，0002-0008 全靠 `inspect()` 防御补丁（0002 docstring 自述曾导致"无法从空库 provision"）。下个大版本重构时一次性修正。
4. **审计表无 `(resource_type, resource_id, created_at)` 索引**——"该文档全部访问记录"这类合规取证查询全表扫；审计表本身无 append-only 保障。
5. **聊天/证据明文入库**，无 at-rest 加密设计；`validate_runtime` 未覆盖 DB/Redis TLS。
6. **根目录 8 个 0 字节乱名文件**（`⚠️`、`实验台：（原始数据` 等——shell 未加引号误创建）+ `.tmp_*`、`agent_lab/` 探针等杂物污染根目录。
7. **前端装了 vitest/msw 却零测试文件**，"半途而废"；`<title>frontend</title>` 未本地化。
8. **`.env.example` 与实际漂移**（Postgres vs SQLite、1536 vs 512 维），新成员按 example 起环境必踩坑。
9. 评测集 v2.1 的 SHA256 在 manifest 与报告间有一字之差；pytest 1020 passed / **14 failed**，全量回归非绿。

## 四、优点（同样重要，值得保持）

1. **fail-closed 哲学贯穿始终**：`validate_runtime`（config.py:166-205）强制 JWT 密钥独立且 ≥32 字节、拒绝身份头伪造、拒绝一切明文 PHI 出口（覆盖 OCR/OpenSearch/对象存储三条通道，正确处理 loopback 与 IPv6）。
2. **认证/授权教科书级**：JWT 固定 HS256 + iss/aud 全 claim 校验；身份头默认不信；恒定时间密码比较消除账号枚举侧信道；双键滑动窗口限流；检索层 `_is_authorized` 二次校验 tenant/patient；`ModelGateway._validate_files` 防合法 document_id 夹带他人对象。
3. **"检索故障"与"证据不足"语义严格分离**（service.py:487-505）——医疗场景极易忽视的正确性问题，做对了。
4. **引用校验防幻觉深度罕见**：句子级引用锚定、诊断性断言拦截+否定豁免、逐句数值+单位核对（带相对容差）、定量结论数值复述。
5. **合规横切真实落地**：consent 是硬门禁（校验 policy_version、撤销即时生效）；外发审计只记 SHA-256 不落原文；多层删除最终一致且异常只记类名防 PHI 泄漏。
6. **测试与 CI 设计专业**：unit/integration/contract/eval/golden 分层（84 个测试文件）；CI 独立迁移 job（upgrade→downgrade→upgrade + alembic check）与部署 job（真实打 /health）；Dockerfile 非 root、迁移不在容器内跑。
7. **评测体系骨架成熟**：dev(14)→Test v1(30)→v2(120)→v2.1(120，含 gold_evidence_groups，manifest+SHA256 冻结)；dev/test 分离纪律严格；A3-hybrid-rrf60 实测 Hit Rate 1.000 / MRR 0.819。
8. **索引设计优于平均**：几乎每个索引都有"为哪条查询服务"的注释；ORM 通用 JSON 与迁移层表达式索引跨方言对齐这个易错点做对了。
