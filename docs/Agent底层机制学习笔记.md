## 0. 一句话心智模型

> **Agent = LLM 当控制器 + 一个反馈回路 + 一组副作用接口。**

把这三样分开看，很多困惑会自动消解：

| 组成 | 性质 | 推论 |
|---|---|---|
| 控制器是**概率性**的 | 输出不可复现 | 测试要靠评估集，不能靠断言 |
| 回路是**无状态**的 | 记忆只是不断增长的数组 | 上下文工程是核心工程，不是「提示词调优」 |
| 副作用**不可逆** | 工具会改数据、发消息、删索引 | 工具层必须当作不可信边界来防护 |

## 1. Agent 的本质：一个带工具的 while 循环

剥到最里层，它就是一个循环：

```python
while True:
    resp = llm(messages, tools)          # 模型推理
    if not resp.tool_calls:              # 模型自己说"不用工具了"
        return resp.text                 # → 退出循环
    for tc in resp.tool_calls:           # 否则执行工具
        messages.append(run(tc))         # 结果写回历史 → 下一轮
```

但真正决定成败的是四个细节，而不是这个骨架本身。

### 1.1 循环的退出条件不在你的代码里

普通 `while` 的终止条件是程序员写死的、确定的；Agent 的退出条件是「这一轮模型没吐 `tool_calls`」——一个**概率性事件**。

→ 所以循环几轮不可预知，必须有硬上限兜底，不能指望模型自觉。

### 1.2 循环体是无状态的，「记忆」全在 messages 数组里

模型每次调用都是一次全新的前向计算，它不「记得」上一轮干了什么。所谓记忆，只是把历史越拼越长地塞回去。

→ 推论：上下文必然膨胀；**往上下文里塞什么，比循环逻辑本身更决定成败**。

### 1.3 「工具调用」不是模型执行了什么

模型输出的只是一段结构化文本：

```json
{"name": "search_public_kb", "arguments": {"query": "..."}}
```

真正动手的是你的代码。**这个边界必须画清楚**：模型是不受信的、会幻觉的，执行层必须做工具名白名单、参数校验、权限审批、超时、结果截断。

把模型输出直接当指令执行，是 Agent 最经典的安全事故。

### 1.4 循环外面还包着一层

| 核心（约 20 行） | 外围设施（几千行） |
|---|---|
| `while` 循环 | 上下文管理（组装 / 压缩 / 记忆分层） |
| | 工具层（声明 / 校验 / 权限 / 沙箱） |
| | 循环控制（步数上限 / 超时 / 成本熔断） |
| | 可观测与状态（trace / 每轮快照 / 可续跑） |

**这个比例就是真实 Agent 工程的比例。** 「写一个 Agent」和「写一个能上线的 Agent」差的就是外围那几千行。

## 2. 循环的四种退出路径

只有第一种是「正常结束」，其余三种都是「护栏兜底」。分开理解比笼统记住「有两种结束方式」有用得多。

| # | stop_reason | 触发条件 | 故障模式 | 对策 |
|---|---|---|---|---|
| 1 | `converged` | 模型没吐 `tool_calls` | 唯一正常结束 | 外部仍需结果校验 |
| 2 | `max_iterations` | 步数用尽，模型未收敛 | 重复调用 / 反复检索同一内容 | 改 prompt 打破循环；检查工具返回是否让它困惑 |
| 3 | `budget_exceeded` | 上下文超硬上限，主动熔断 | 工具返回过大 + 轮次过多 | 降低 `keep_recent_turns`；缩短工具返回 |
| 4 | `context_overflow` | 模型窗口真超了，网关报错 | 预压缩策略失效 | **确定性失败**，重试无用，必须降级 |

### 2.1 关键洞察：护栏要按「谁先到」排序

**上下文是每一轮都在增长的，而步数上限是固定的。所以上下文这道闸，通常比步数闸更早到达。**

本机实测（runaway 场景，工具每轮返回约 346 字符）：

```
budget_exceeded  在第 52 轮触发 / 18143 字符
max_iterations   设为 60，根本没到
```

也就是说：`max_iterations` 是「事后补救」，`budget_exceeded` 是「事前拦截」。**你以为 8 次迭代是安全网，实际在长任务里上下文早就先爆了。**

### 2.2 确定性失败 vs 瞬时失败

这两类错误混在一起处理，是 Agent 线上事故的常见来源：

| | 判定 | 该做什么 |
|---|---|---|
| 上下文超限 | **确定性失败**，重试必然再失败 | 降级：压缩后重试 / 换小任务 / 直接放弃 |
| 限流、网络抖动 | 瞬时失败 | 退避重试 |

对确定性失败做无限重试，就是烧钱。

### 2.3 converged ≠ 成功

`converged` 只是「模型认为可以作答了」，它可能只是**误以为**完成了。所以循环外面还要再套一层结果校验（schema 校验、事实核查、人工复核）。

**循环退出 ≠ 可以交付。**

## 3. 上下文压缩：它推迟熔断，但不消除熔断

### 3.1 一个常见的错误前提

> 「超过某个值就压缩，所以不会撞上窗口上限。」

**实测结论：不是这样。压缩只改变「什么时候撞」，不改变「会不会撞」。**

两条轨迹对比（同一场景）：

| 模式 | 熔断轮次 | 压缩间隔 | 压缩后基线 |
|---|---|---|---|
| 不压缩 | 第 52 轮 | — | — |
| **压缩生效** | **第 121 轮，仍然熔断** | 9→6→4→2→1→1→1… | 3078→17916 |

注意那串间隔——它在**崩塌**。

### 3.2 根因：摘要「追加」而不是「合并」

```
_split_into_turns() 把 messages 切成 head(固定头部) + turns(可压缩轮次)
                                    ↑
                        压缩摘要被放进了 head
                        而 head 永远不参与压缩
```

于是每轮压缩都往 head 追加约 400 字符的**永久占用**：

```
每轮压缩 → head 永久增长 → 基线抬高 → 压缩间隔缩短
        → 最终即使每轮都压缩，也压不回预算内
```

这叫**压缩跑步机（compaction treadmill）**。危害是**隐性**的：不报错、不告警，只是成本缓慢上升，然后在某个长任务里突然熔断。

### 3.3 修复与验证

修复方式：把旧摘要从头部摘出来，与新折叠的内容**合并成一条**，并给摘要设体积上限（本脚本 1200 字符）。

修复后实测：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 压缩间隔 | 9→6→4→2→1→1… 崩塌 | **恒定 10** |
| 压缩后基线 | 3078→17916 抬升 | **恒定 2784** |
| 结果 | 第 121 轮熔断 | **200 轮无熔断** |

### 3.4 健康判据（只有两个）

1. **压缩间隔是否稳定**
2. **压缩后基线是否恒定**

这两个一旦漂移，就是跑步机。

### 3.5 可迁移的结论

1. **压缩买的是「更多轮次」，不是「无限轮次」。** 它把 52 变成 121，仅此而已。
2. **压缩和步数上限要一起算账。** 不能因为「有压缩了」就把 `max_iterations` 设很大——它们会互相遮蔽对方的失效。
3. **真正的解法是减少每轮增量**：缩短工具返回、精简 prompt、剔除冗余历史。
   **增量不变，任何压缩策略最终都会输。** 压缩是管理症状，减少增量才是治本。

> 对 RAG 项目的直接映射：检索返回就是最大的增量来源。调 `top_k` 时省下的不只是延迟，还有 Agent 的可用轮数——**检索质量和上下文预算是一笔账，不是两笔。**

### 3.6 一个必须知道的实现约束

压缩必须在**「轮」的粒度**上做，不能随手删单条消息。

OpenAI 协议要求每个 `tool_call_id` 都有对应的 tool 消息，拆散了整个请求会被网关拒绝。所以一轮 = 一条 `assistant(tool_calls)` + 紧随其后的所有 tool 结果，是**不可分割的原子单元**。

## 4. Python 基础补强：三个容易混淆的认知

### 4.1 两类类：数据类 vs 服务类

```python
@dataclass
class ToolCall:              # 数据类：只是字段容器
    id: str
    name: str
    arguments: dict

class ScriptedModel:         # 服务类：持有可变状态 + 方法
    def __init__(self, plan):
        self._plan = plan
        self._cursor = 0
    def complete(self, ...): ...
```

| | 数据类 | 服务类 |
|---|---|---|
| 特征 | 无 `__init__`（`@dataclass` 自动生成） | 手写 `__init__` + 方法 |
| 判据 | 只是「一堆字段的容器」 | **有没有需要跨调用保持的状态** |

**判据很简单：看这个类有没有状态。**

- `ToolCall` 不需要「记住」任何东西 → `@dataclass` 够了
- `ScriptedModel` 必须记住「上次读到第几条」→ 必须手写 `__init__`

如果 `ScriptedModel` 没有 `_cursor`，它的 `complete()` 就退化成纯函数，**根本不需要类**。所以 `__init__ + 方法` 是「有状态」的必然结果，不是风格选择。

> 这也解释了为什么工具函数可以直接写成普通函数（`search_public_kb(query)`）——工具是**无状态**的，同样输入给同样输出，不记得上次查过什么。

### 4.2 `__init__` 是「建立初始状态」，不是「记录状态」

看 `ScriptedModel.__init__` 存的两类东西：

```python
def __init__(self, plan):
    self._plan = plan       # 配置：构造后永不变，只读
    self._cursor = 0        # 状态：每次调用都变，可写
```

实测：

```
调用 m1.complete() 一次后：
  m1._cursor = 1   ← 变了
  m2._cursor = 0   ← 没变（每个实例有自己的一份）
```

**`__init__` 只负责给 `_cursor` 一个起点（0）。真正「记录」状态的是 `complete()` 里的 `self._cursor += 1`。**

| | 谁来做 | 做什么 |
|---|---|---|
| 配置 | `__init__` | 装进去，之后只读（`_plan`、`max_iterations`、`api_key`） |
| 状态 | `__init__` 建初始值 + **方法改写** | `_cursor` 从 0 开始，每轮 +1 |

**为什么必须写在 `__init__` 里？** 因为写在外面会变成**类变量**，被所有实例共享：

```
BuggyModel（类变量 _cursor = 0 写在类上）:
  a.complete()=1  b.complete()=2  a.complete()=3
  → a 和 b 共享同一个计数器！b 的调用污染了 a

GoodModel（self._cursor = 0 写在 __init__ 里）:
  c.complete()=1  d.complete()=1  c.complete()=2
  → 各自独立
```

⚠️ **类属性是可变对象时最危险**：`items = []` 会让所有实例共享同一个 list，一个 `append` 影响全部。这和「忘记在 `__init__` 里初始化」是同一个 bug 的两种写法。

> 实用判据：**`__init__` 里不该有业务逻辑。** 如果里面调用了网络、读写文件、做计算，通常意味着设计有问题。`__init__` 只做「把状态摆好」。
>
> 顺带解释一个反直觉设计：为什么它叫**初始化方法**而不是构造函数？因为真正创建对象的是 `__new__`，`__init__` 只是在对象建好之后**给它装初始状态**。名字本身就说明了定位。

### 4.3 `self.messages` 不是全局变量

```python
def __init__(self):
    self.messages = []      # ← 这里其实有两个东西，归属完全不同
        ↑        ↑
     局部变量   实例属性
```

**`self` 是局部变量**（方法的参数）；**`self.messages` 是属性**，存在实例的 `__dict__` 里。

实测：

```
d.__dict__ = {'messages': ['hello']}     ← 属性存在实例上
'messages' in Demo.__dict__   -> False   ← 不在类上
'messages' in globals()       -> False   ← 不在模块全局
a.messages is b.messages      -> False   ← 各实例独立（铁证）
a.class_level is b.class_level -> True   ← 类属性才是真共享
```

最硬的证明：在方法里写裸 `messages`（不带 `self.`）会直接报错：

```
裸 messages -> NameError: name 'messages' is not defined
```

**如果 `self.messages` 是全局变量，裸 `messages` 就该能读到它。**

### 4.4 属性查找 ≠ 作用域查找

这是两套完全不同的机制：

```
作用域查找（L→E→G→B）              属性查找（实例 → 类 → 父类/MRO）
  局部 → 外层函数 → 模块全局 → 内置
```

`self.messages` **不在这条作用域链的任何一层上**。

### 4.5 四种写法完整对照（建议记住）

| 写法 | 存在哪 | 共享范围 | 查找机制 |
|---|---|---|---|
| `messages = []`（方法内） | 栈帧局部 | 仅本次调用 | 作用域 |
| `self.messages = []` | 实例 `__dict__` | **该实例**的所有方法 | 属性 |
| `class_level = []`（类体） | 类 `__dict__` | **所有实例** | 属性（先实例后类） |
| 模块级 `X = []` | 模块 `__dict__` | 整个模块 | 全局 |

**判断是不是全局，标准只有一个：换个实例还看得到吗？** 看不到，就不是全局。

> 「活得久」≠「全局」。`self.messages` 容易让人误以为是全局，恰恰因为它比局部变量活得久（实例不回收它就在）。但它的可见范围被严格限制在**那一个实例**里。

## 5. 会话状态放错位置 → 跨用户泄漏

### 5.1 错误写法与后果

```python
class AgentRuntime:
    def __init__(self):
        self.messages = []          # ← 灾难的起点：状态在实例上
    def run(self, task):
        self.messages.append(...)
```

双用户并发实测：

```
错误示范（messages 挂在 self 上，服务共用一个实例）：
  用户A 这一轮发给模型的上下文 = 8 条，其中 4 条是用户B 的数据
  用户B 这一轮发给模型的上下文 = 7 条，其中 3 条是用户A 的数据

正确示范（messages 是 run() 的局部变量）：
  用户A = 4 条，全是自己的；用户B = 4 条，全是自己的
```

### 5.2 关键机理：Agent 的一次请求不是原子的

它要跑多轮循环，每轮有一次模型调用（几百毫秒到几十秒）。**在这段时间里，另一个用户的请求完全会插进来**，两边往同一个 list 里 `append`。

所以这不是「小概率竞态」，而是**只要服务并发就必然发生**。

注意泄漏是**不对称的**（4 条 vs 3 条）：除了共享 list，还叠加了 `append` 的竞态——说明 B 是在 A 还在写的过程中读的。

### 5.3 为什么这个 bug 特别容易犯

因为把 `AgentRuntime` 从「单次运行」改成「支持多轮对话」时，最自然的写法就是把 `messages` 提到 `self` 上。**单用户测试全过，上生产两个人同时用就串了。**

### 5.4 判据表

| 类型 | 能不能放 `self` |
|---|---|
| 配置（构造后只读） | ✅ 可以，而且应该 |
| **每请求状态**（对话历史、当前轮次、累积证据） | ❌ **绝不能** |

**自查方法：搜索方法体内的 `self.xxx =` 赋值。** 只要出现，就问一句「这个状态是每个请求独立的吗？」——是，就是 bug。

### 5.5 对医疗场景的特别警示

这个 bug 的危害不是权限判断错误，而是**上下文串号**——A 患者的检验结果被当成 B 患者的证据喂给模型。

**危害和越权泄漏完全一样，但绕过了所有权限检查**，因为权限检查在检索层是对的，污染发生在**组装上下文之后**。

→ 所以「安全三项零容忍」里的**复核泄漏**，检查范围要覆盖**上下文组装层**，不能只查检索层。

## 6. LangGraph：reducer 到底对应我们代码的哪一部分

### 6.1 正确类比

```python
# 手写（命令式）：合并逻辑在【循环里】
messages.append(assistant_msg)
messages.append(tool_msg)

# LangGraph（声明式）：合并逻辑在【状态 schema 上】
class State(TypedDict):
    messages: Annotated[list, add_messages]     # ← 就是这一行
# 节点只需 return {"messages": [新增的]}，不关心怎么合并
```

**reducer 对应的不是 `messages` 这个变量，而是 `messages.append(...)` 这个「动作」。** 它把「怎么合并」从循环体里抽出来，声明到类型上。

### 6.2 实验：忘了写 `Annotated` 会静默丢历史

```python
class StateNoReducer(TypedDict):
    messages: list              # 忘了写 Annotated
```

实测：

```
有 reducer：['human:用户提问', 'ai:A 的回复']       ← 追加，历史保留
无 reducer：['assistant:B 的回复']                  ← 覆盖！用户提问没了
```

**没有报错，没有警告。** 这是 LangGraph 新手最常见的坑。

### 6.3 reducer 的真正动机：并行分支

```python
g.add_edge(START, "b1")     # 两条边都从 START 出发
g.add_edge(START, "b2")     # = 两个节点并行执行
```

实测两个分支的产出都被合并了。

**关键洞察：单线性循环里根本用不上 reducer。** 手写 `while` 是顺序的，永远不会有两个节点同时写 `messages`。**reducer 是为并行 / 分支而生的**——当两个节点同时返回 `{"messages": [...]}`，框架必须知道「该合并还是该覆盖」。

### 6.4 额外发现：`add_messages` 比 `list.extend` 聪明

```python
add_messages([{content:"v1", id:"1"}], [{content:"v2", id:"1"}])
→ [{content:"v2", id:"1"}]      # 同 id 的消息被「更新」，不是重复追加
```

**对手写代码的启发**：如果将来要做「重试某一步」或「修正历史中的某条消息」，裸 `append` 做不到，需要按 id 去重更新。

## 7. 从 while 循环到 StateGraph：逐行映射

### 7.1 映射表

| 手写 `while` 循环 | LangGraph | 是什么 |
|---|---|---|
| `messages = [...]` 局部变量 | `class State(TypedDict)` | 状态容器 |
| `messages.append(...)` | `Annotated[list, add_messages]` | 合并规则 |
| `reply = model.complete(...)` | `add_node("agent", agent_node)` | 节点 1 |
| `for c in reply.tool_calls: run(c)` | `add_node("tools", tools_node)` | 节点 2 |
| `if not reply.wants_tools: break` | `add_conditional_edges(..., →END)` | 条件边 |
| **`while` 回到开头** | **`add_edge("tools", "agent")`** | **回边** |
| `for i in range(max_iterations)` | `config={"recursion_limit": 6}` | 迭代上限 |

**核心：一个 `while` 循环 = 两条边 + 一个条件边。**

- **回边**（tools → agent）让图成环，这就是「循环」的来源
- **条件边**（agent → END）负责退出

### 7.2 实测对齐

用同一个剧本、同一个工具注册表搭两个完全相同的 Agent：

```
手写循环    答案：根据公共知识库：一线降压药包括 ACEI、ARB、CCB、利尿剂等。  messages=4
StateGraph  答案：（完全相同）                                  messages=4
两者答案一致：True     agent 节点被调 2 次 / tools 节点被调 1 次
```

### 7.3 踩坑实录：框架会「翻译」你的数据

第一次跑 StateGraph 版直接报错 `KeyError: 'function'`。

原因：`add_messages` 会把消息**规范化**成 LangChain 的 `AIMessage`，`tool_calls` 结构跟着变了：

```python
# OpenAI 原始格式
{"function": {"name": "search_public_kb", "arguments": '{"query":"..."}'}}

# LangChain 规范化后
{"name": "search_public_kb", "args": {"query": "..."}}   # args 已解析成 dict
```

**框架「统一数据格式」既是封装的好处，也是踩坑点**——你的代码不再认原来的格式了。写节点时必须兼容两种，或者一开始就用框架的消息类型。

> 这个坑很能说明问题：**封装不是免费的，它会把你的数据翻译成它自己的方言。**

## 8. 框架是不是就是封装？

**对了一半。封装只是第 1 层，真正重要的是第 2、3 层。**

### 第 1 层：封装（省力）

把 while、状态合并、重试、并发调度都包起来。这层确实就是封装。

### 第 2 层：把控制流从「代码顺序」变成「数据结构」← 质变在这里

```
手写版：控制流在【栈帧】里 —— "第 3 行之后跑第 4 行"，隐式、不可检查
图版本：控制流在【数据结构】里 —— 节点和边是对象，可被检查、可视化、序列化
```

### 第 3 层：因为第 2 层才可能有的能力 ← 用框架的真正理由

| 能力 | 手写循环 | 为什么 |
|---|---|---|
| checkpoint 持久化（挂了从断点续跑） | ❌ | 执行位置在栈帧里，没法序列化 |
| 时间旅行回放 | ❌ | 同上 |
| 并行分支 | 要自己写并发 | 图的拓扑天然支持 |
| 人审中断（interrupt） | 要自己写状态机 | 图可在任意节点暂停 |

**注意那些「做不到」——不是代码写得不好，而是控制流在栈帧里，不在数据结构里。** 你没法把「栈帧」存进数据库然后换个进程恢复。

### 选型判据

> **我需要 checkpoint / 并行 / 回放 / 人审中断吗？**

- **不需要** → 手写循环更透明、更好调试。**教学脚本就是这类。**
- **需要** → 框架那点复杂度是值得的，否则你要自己重新发明一个状态机。

**一句话：封装省的是打字，换范式省的是「重新发明状态机」。** 前者是量变，后者是质变。

### 学习顺序建议

**先手写循环理解机制，再看框架。**

反过来先学框架，容易变成「会调 API 但不知道底下发生了什么」，遇到 bug 只能靠猜。上面那个 `KeyError: 'function'` 就是例子——**如果没写过手写循环，不会立刻知道「是框架把 tool_calls 结构改了」**，只会觉得框架有 bug。

**理解底层的人，看框架的报错是透明的。**

### 反例对照的量化证据

同一个 runaway 场景，开关防护的差距：

```
正常模式：8 轮熔断 →  18 条消息 /  2,919 字符
--naive ：402 条消息 / 69,351 字符（跑满 200 轮）
```

**43 倍差距。** 这是「为什么必须有 `max_iterations`」的量化答案。

### 阅读脚本的建议顺序

1. 文件头部的三原则 + 四种退出路径（先建立心智模型）
2. `AgentRuntime.run()` —— 核心 while 只有约 20 行
3. `ToolRegistry.dispatch()` —— 五道防护，理解「工具层是不可信边界」
4. `compact()` —— 压缩跑步机与合并摘要
5. `_split_into_turns()` —— 为什么压缩必须在「轮」粒度上做

## 10. 一页速查

| 主题 | 一句话结论 |
|---|---|
| Agent 本质 | LLM 当控制器 + 反馈回路 + 副作用接口 |
| 循环退出 | 4 条路径，只有 `converged` 是正常结束 |
| 护栏排序 | 按「谁先到」排，不按「谁更重要」排 |
| 上下文 vs 步数 | 上下文每轮都长，步数固定 → 上下文闸先到 |
| 压缩的本质 | 买「更多轮次」，不是「无限轮次」 |
| 压缩健康判据 | 间隔稳定 + 基线恒定 |
| 压缩的根本解 | 减少每轮增量（增量不变，任何策略最终都会输） |
| 压缩实现约束 | 必须在「轮」粒度上做，否则网关拒收 |
| 类的判据 | 有没有需要跨调用保持的状态 |
| `__init__` | 建立初始状态（不是记录），保证实例独立 |
| `self.x` | 实例属性，走属性查找，不是作用域 |
| 状态放哪 | 配置可以放 `self`；每请求状态绝不能 |
| 自查方法 | 搜索方法体内的 `self.xxx =` |
| reducer 对应 | 不是 `messages` 变量，是 `messages.append` 动作 |
| reducer 动机 | 并行分支，不是单线性循环 |
| StateGraph | 一个 while = 两条边 + 一个条件边 |
| 框架 | 封装（量变）+ 换范式（质变）+ 新能力 |
| 选型判据 | 需要 checkpoint / 并行 / 回放 / 中断吗？ |
