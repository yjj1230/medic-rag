# 功能开发流程（需求受理 → 交付）

> 适用对象：任何从业务方接到功能需求、并负责落地的人。
> 配套技能链：`brainstorming`（澄清+设计）→ `writing-plans`（拆计划）→ `executing-plans` 或 `subagent-driven-development`（逐任务执行）→ `verification-before-completion`（收尾验证）；过程中遇到缺陷用 `systematic-debugging`。

---

## 0. 一句话版本

**业务员的话 → 澄清成可验证的验收标准 → 2-3 个方案 → 设计文档（用户批准）→ 任务计划 → 逐任务 TDD 执行 → 真实链路验证 → 显式上报偏差。**

---

## 1. 前提认知：业务员给的不是需求

业务员说的是**他想要的画面**（"加个导出按钮"、"能不能自动填"、"这里能不能快点"），不是**需求**。他从自己的岗位视角描述现象和方案，而你要的是场景与目标。

所以第一件事永远是翻译，四个必问方向：

| 问什么 | 为什么 |
|---|---|
| 你在什么场景下遇到这个问题？ | 定位真实场景，而不是他猜的解法 |
| 现在你是怎么绕过它的？ | 现状成本决定这件事值不值得做 |
| 做成什么样你就满意了？ | 这才是验收标准的原料 |
| 什么情况下它不需要做？ | 划边界，防止范围蔓延 |

> 反例：业务员说"加个批量导出"。真实场景可能是"月底要手工抄 200 条数据给财务"——那么真正的需求可能是"财务能直接看到数据"，导出只是他想到的一种手段。

## 2. 八步流程

| # | 步骤 | 动作 | 产出物 | 门禁 |
|---|---|---|---|---|
| 1 | 受理 | **原话**记录诉求，不转述不润色 | 需求条目（见 §4 模板） | — |
| 2 | 澄清 | 一次只问一个问题：目的/谁用/成功标准/边界/不做什么 | 共识 | 未澄清不得进入第 3 步 |
| 3 | 方案 | 给 2-3 个方案，含取舍与明确推荐 | 方案对比 | — |
| 4 | 设计 | 讲清架构、数据流、错误处理、测试点 | `specs/YYYY-MM-DD-<主题>-design.md` | **用户批准才能动代码** |
| 5 | 自检 | 扫占位符/自相矛盾/歧义/范围过大 | 修订后的 spec | — |
| 6 | 计划 | 拆成可独立验证的小任务，每个任务写清怎么算完成 | `plans/YYYY-MM-DD-<主题>-implementation.md` | 用户过目 |
| 7 | 执行 | 逐任务实现，**先写失败测试再实现** | 代码 + 测试 | 每任务两阶段评审 |
| 8 | 验证 | 跑真实链路，收集证据 | 测试输出/接口响应/日志 | 不通过不算完成 |

### 步骤 2：澄清（一次一个问题）

一次抛 5 个问题，对方只会回答最省力的那个。**一条消息只问一个问题**，优先给选择题。

澄清完成的标准：能写出下面这句话且无歧义——
> 当 **(谁)** 在 **(什么场景)** 下，需要 **(做什么)**，成功表现为 **(可观测结果)**；本次**不包含** (边界)。

### 步骤 3：方案对比

永远给 **2-3 个**方案，先说推荐项和理由，再说其他选项的代价。只有一个方案时，说明你还没探索。

### 步骤 4：设计文档（spec）

路径固定：`docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`。按现有 spec 的结构写：

```
1. 背景                     ← 业务场景、现状痛点、为什么现在做
2. 目标与非目标             ← 非目标写不清，范围一定失控
3. 总体架构                 ← 组件、边界、数据流
4. 核心数据契约             ← 关键结构体/接口/枚举，字段级
5. 设计细节                 ← 分模块展开
   ...                      ← 错误与降级、权限与安全、性能
N. 实施阶段                 ← 分片交付，每片可独立验收
N+1. 验收标准               ← 可观测、可复现
```

**必须写进 spec 的内容（最容易漏）：**

- **安全/合规不变量**：例如"患者证据必须带可定位引用才能被检索"、"审查未通过的文档可留存但不可检索"、"公共记录不得携带租户/患者 ID"。
- **错误与降级**：外部依赖不可用时，是报错、降级还是排队？降级后用户看到什么？
- **非目标**：这次明确不做什么，以及为什么。

### 步骤 5：spec 自检（写完立刻做）

1. **占位符扫描**：还有 `TBD`/`TODO`/含糊表述吗？
2. **一致性**：各节之间矛盾吗？架构与功能描述对得上吗？
3. **范围**：能用一个实施计划做完吗？做不完就拆成多个子项目，各自走一轮 spec→plan。
4. **歧义**：哪条需求有两种读法？选一种并写死。

### 步骤 6：实施计划（plan）

路径固定：`docs/superpowers/plans/YYYY-MM-DD-<主题>-implementation.md`。结构：

```
# <主题> Implementation Plan
## Global Constraints          ← 全局约束（技术栈、不可破坏的既有契约）
### Task 1: <可独立验收的任务>
- [ ] Step 1: Write the failing tests
- [ ] Step 2: Run the tests and verify they fail
- [ ] Step 3: Implement ...
- [ ] Step 4: Run the tests and existing suite
### Task 2: ...
## Plan Self-Review
```

**关键要求：**

- 每个任务**能独立验收**（有自己的测试与通过标准），不要"大爆炸式"一步到位。
- 每个任务内部按 **TDD 顺序**列步骤：先写失败测试 → **确认它真的失败** → 再实现 → 再验证。缺了"确认失败"这一步，你无法证明测试有效。
- 计划里写明**怎么验证**，而不是"完成后检查一下"。

### 步骤 7：执行

- 逐任务推进，**一个任务做完并验证再开下一个**（任务之间并行时注意共享文件冲突）。
- 每个任务两阶段评审：①**规格符合性**——是否照 spec 做了、有没有多做或少做；②**代码质量**——是否有重复、耦合、命名不清、破坏既有契约。
- 不满足就退回重做，不要"先记下来以后改"。

### 步骤 8：验证（证据，不是感觉）

**必须跑真实链路**，不能只看单测绿：

- 单元/契约测试：全量跑，记录通过数
- 真实依赖：数据库、索引、外部服务用**真环境**跑一次端到端
- 安全不变量：逐条断言（无残留、无越权、无缺引用）
- 外部依赖不可控时：写清"哪些是环境限制、哪些是代码问题"

## 3. 四条硬规则

### 规则 1：需求必须可验证

"能回答患者问题"是假的验收标准；"上传 → 解析 → 命中证据 → 带引用回答"才是真的。

> **真实案例**：本项目三个致命缺陷——模型适配器漏导入异常类、OpenSearch 批量写入参数非法、私有记录缺引用字段——**单元测试全部通过**，只有在真实全栈跑起来时才暴露。根因是验收标准停留在"单测绿"，没有定义可观测的端到端链路。

### 规则 2：隐性不变量必须写进文档

只活在代码实现里的约束，等于没有约束——后来人不会读代码悟出来。

> **真实案例**：检索侧要求引用四要素齐全（`source_id`/`title`/`version`/`location`），这条规则只存在于一个 `_has_citation` 函数里，从未写进 spec。结果写入侧从不填其中两个字段，患者证据**能入库却永远检索不到**，表现为"问自己的报告永远答不出来"。修复只花了几行，但排查花了很久。

### 规则 3：设计未批准，不写代码

包括"这么简单不用设计"的情况。一个按钮的改动，设计可以是三句话，但**必须有那三句话并得到确认**。跳过这步省下的十分钟，通常在返工时以十倍偿还。

### 规则 4：偏差要显式上报，不许静默绕过

改不了的环境、替代实现、临时降级、暂时关闭的校验——全部写进交付说明，并说清原因和恢复条件。

> **真实案例**：因权限限制无法停用占用端口的系统服务，只能改用备用端口；因外部模型网关不提供向量接口，只能以关键词检索模式运行。这两条都写进了交付说明，而不是悄悄留在配置里。

## 4. 需求受理模板（直接复制使用）

```markdown
## 需求：<一句话标题>
- 受理日期：
- 提出人/岗位：
- 原始诉求（原话，不改写）：

### 澄清记录
- 场景：
- 现状与绕过方式：
- 成功标准（可观测）：
- 边界（本次不做什么）：
- 依赖与风险：

### 结论
- 验收标准（可复现的链路描述）：
- 影响的既有契约/不变量：
- 关联 spec / plan：
```

## 5. 完成判定清单

功能只有在**全部**满足时才算完成：

- [ ] spec 已批准，且已实现其中全部目标
- [ ] spec 中的非目标确实没做
- [ ] 计划的每个任务都完成并独立验收
- [ ] 全量测试通过（记录通过/跳过数量）
- [ ] 真实链路端到端跑通，有输出证据
- [ ] 安全/合规不变量逐条断言通过
- [ ] 错误与降级路径验证过（外部依赖不可用时的行为）
- [ ] 偏差与遗留项已显式记录（含原因与恢复条件）
- [ ] 临时文件/调试脚本已清理，仓库无残留

## 附：常见反模式

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 听完需求直接开写 | 做出来的不是对方要的 | 先澄清，一次一个问题 |
| 只给一个方案 | 掩盖了更优解与代价 | 2-3 个方案 + 推荐 |
| 需求写成"优化体验" | 无法验收，无法结项 | 写成可观测链路 |
| 计划不拆任务 | 无法中途验证，风险后置 | 拆成可独立验收的小任务 |
| 跳过"确认测试失败" | 测试可能是空转的 | 先看它真的失败 |
| 只跑单测就交付 | 集成缺陷漏到线上 | 真实链路端到端验证 |
| 隐性约束只写代码 | 后人踩坑、数据静默不可用 | 不变量写进 spec |
| 环境限制悄悄绕过 | 上线才发现行为不一致 | 显式上报偏差 |
