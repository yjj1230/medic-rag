## 一、ENV-2：本地联调实例无法启动（fail-closed 误伤）

### 1.1 现象（复现证据）
按当前源码启动后端两次均失败：

```
ValueError: 配置不安全：开发/测试环境也不得通过远程明文 HTTP 发送 PHI；
请改用 HTTPS 或回环地址（涉及 MODEL_GATEWAY_URL）
```
（第二次追加 `涉及 OCR_SERVICE_URL`）

- 触发点：`core/config.py:206-215`（`validate_runtime()` 的 dev 分支）。
- 涉及配置：`MODEL_GATEWAY_URL=http://121.40.34.96:18097/v1`、`OCR_SERVICE_URL=http://192.168.254.35:18080`。
- 关键事实：**网关不支持 HTTPS**（实测 `https://121.40.34.96:18097` TLS 握手失败 `SEC_E_INVALID_TOKEN`；`http://` 返回 401＝需鉴权，即服务本身正常）。故"改走 HTTPS"在本地不可行。

### 1.2 根因
这是 P0-4（明文 PHI 出网由告警升级为阻断，见 `docs/P0_P1_修复报告.md:100`）**刻意引入**的安全姿态。
对生产部署正确；但本地联调必须用真实网关（默认无 HTTPS），于是**必然无法启动**，且无任何豁免出口
（`plaintext_phi_egress_warnings()` 仅剩提示用途，被 dev 分支的 `raise` 挡在前面）。

### 1.3 决策：新增开发期显式豁免开关（默认关闭）
与既有 `allow_insecure_identity_headers` 完全同构——**默认关闭 + 仅开发环境生效 + 非开发环境启用即致命**。

| 项 | 设计 |
|---|---|
| 新配置 | `allow_plaintext_phi_egress: bool = False`（env `ALLOW_PLAINTEXT_PHI_EGRESS`） |
| dev 分支 | 仅当该开关为真时放行远程明文；否则维持现状 `raise` |
| 非开发环境 | 该开关为真 → 计入 `problems`，**拒绝启动**（与身份头开关同规格） |
| 回环地址 | 无论开关与否一律放行（现状不变） |
| 既有测试 | `test_development_rejects_remote_plaintext_phi_egress` 不传该开关 → 仍 `raise`，**保持绿** |

**为何不选另两条路径**：① HTTPS 网关不可用（见 1.1）；② 改 `.env` 指向回环 sidecar 需要真实网关能力（问答断言依赖真实模型），回环占位等于放弃 B/D/F 组验收目标。

### 1.4 验收标准
1. 新增/修改单测：开关默认关闭时 dev 仍拒绝；开启时 dev 放行；非开发环境开启 → 拒绝启动。
2. 全量 pytest 无新增失败（本机既有基线例外：20 failed / 9 errors，与业务无关）。
3. `.env` 增加 `ALLOW_PLAINTEXT_PHI_EGRESS=true` 后，后端可用**真实网关**启动，`/health` 200。
4. 启动日志出现明文外发告警（可观测性保留，不静默）。

### 1.5 风险与边界
- 该开关使本地实例可向远程明文外发 PHI → **仅限本地联调**；生产环境由 1.3 的致命校验兜住。
- 生产启用路径（`is_dev_environment=False`）不受本改动影响。

## 二、P0-6：`DELETE /v1/documents/{id}` 恒 500

### 2.1 现象（复现证据，累计 3/3）
旧代码进程与新代码进程均复现：`DELETE` → 500，DB `documents.status` 保持 `READY`（无墓碑），私有索引残留 1 条。
证据：`eval_out/_delete_probe.txt`、`eval_out/e2e_retest_a02a03.json`。

### 2.2 根因
`api/routes/documents.py:119` 依赖 `get_private_index_writer`，而后者读
`request.app.state.private_index_writer`（`api/dependencies.py:64-96`）；
`api/app.py` 的 `lifespan` **从未装配** `app.state.private_index_writer`（该文件已注释说明"索引写入属于
worker 进程"）。于是依赖在**进入处理器之前**抛 `RuntimeError("private index writer is not configured")`
→ 全局无该异常处理器 → 500。

### 2.3 修复方向（须在 §2.4 评审后定稿，不预判实现）
- **方向 A**：API 启动时装配 `private_index_writer`（复用 `scripts/run_worker.py` 的 `OpenSearchIndexWriter` 构造，
  `visibility="private"`）。属"API 进程也写索引"，与既有架构注释冲突，需评估。
- **方向 B**：删除走**异步任务**（投递到 worker 消费），API 只登记删除意图，返回 202/200 回执；
  索引删除由 worker 执行。契合既有架构（写入归 worker），且天然可重试。
- **方向 C**：API 装配 writer 仅用于删除，写入仍归 worker（最小改动，但仍是双写者）。
- 无论哪条，**必须满足**：删除后索引与 DB 均无残留（三处：索引 / DB / 对象存储），且失败不得报成功。

### 2.4 待决策
方向 A/B/C 的取舍需你（或架构 owner）拍板——尤其"索引写入是否允许出现在 API 进程"这条既有边界。
**未定稿前不写生产代码。**

### 2.5 验收标准（定稿后）
1. G-02 用例：删除后 `index_residual_count == 0`、DB 墓碑就位、对象存储对象不可达。
2. 破坏性验证：索引不可达时删除**不得**报成功（`failed_layers` 非空）。
3. 幂等：重复 DELETE 返回一致回执，不产生二次副作用。
