# 多问题查询处理设计

- **日期**：2026-10-15
- **状态**：设计稿，待评审
- **目标**：让一条消息中的多个独立问题能够被识别、独立检索、分别校验证据，并按原顺序生成可追溯答案。

## 1. 背景与现状

当前项目把整段输入作为一条查询处理：归一化、单一意图识别、上下文补全、构造一条 `SearchQuery`、BM25 与向量混合检索、一次模型生成、整体引用校验。`ProcessedQuery` 没有子问题集合，编排器也只调用一次检索服务。

因此，输入“我的血红蛋白是多少？白细胞正常吗？高血压平时要注意什么？”时，系统不能保证三个问题都分别有证据、分别得到回答。相关代码位于：

- [query/pipeline.py](../../src/medical_rag/query/pipeline.py)
- [query/contracts.py](../../src/medical_rag/query/contracts.py)
- [chat/orchestrator.py](../../src/medical_rag/chat/orchestrator.py)
- [retrieval/contracts.py](../../src/medical_rag/retrieval/contracts.py)

## 2. 目标与范围

### 目标

1. 识别一条消息中的多个独立问题。
2. 每个子问题独立归一化、识别意图和计算检索策略。
3. 每个子问题独立执行 BM25、向量检索、RRF 和相关性门禁。
4. 独立检索任务采用受限并行，降低总延迟。
5. 对每个子问题单独判断证据是否足够，并单独绑定引用。
6. 按原始顺序生成答案，避免漏答或跨题引用。
7. 保持单问题请求兼容，并为拆分失败提供安全回退。

### 非目标

本设计不改变文档入库、切块、Embedding 或索引结构；不绕过 tenant、patient、consent 权限；不在第一阶段引入复杂的多跳图搜索；多轮历史仍由现有上下文补全处理，不把历史消息当成当前消息中的子问题。

## 3. 总体方案

采用“规则优先、模型兜底”的混合拆分方案：

- 规则识别问号、分号、换行编号和“另外、同时、以及、还有”等并列连接词。
- 规则结果满足完整性和置信度条件时直接使用。
- 长句、多意图或边界不明确时，才调用受控的查询改写模型。
- 模型输出必须通过结构校验、原文覆盖校验和安全复核。
- 拆分失败时回退到现有单查询链路，不把不确定拆分结果直接用于医学回答。

### 3.1 查询路由层

拆分之前增加 `QueryRouter`，先决定当前请求是否需要拆分。路由是多问题处理的入口，不能把所有请求都直接送入拆分器。

建议路由结果包括：

```python
class QueryRoute(StrEnum):
    SAFE_BLOCK = "safe_block"
    SINGLE_QUERY = "single_query"
    MULTI_QUERY = "multi_query"
    MULTI_HOP = "multi_hop"
```

路由判断依据：

1. 安全分类结果；高风险请求直接进入 `SAFE_BLOCK`。
2. 是否存在多个独立的疑问意图，而不是简单的并列名词。
3. 子问题之间是否共享同一个答案上下文。
4. 后一个问题是否依赖前一个问题的答案。
5. 问号、编号、分号和“另外/同时/还有”等连接词等结构信号。
6. 规则置信度；置信度不足时优先走 `SINGLE_QUERY`，避免误拆分。

路由示例：

| 输入 | 路由 | 原因 |
|---|---|---|
| “我的血红蛋白是多少？白细胞正常吗？” | `MULTI_QUERY` | 两个独立指标问题，应分别检索和回答 |
| “血压和血糖的正常范围是什么？” | `SINGLE_QUERY` | 一个共同主题下的范围说明，可以统一回答 |
| “我的血红蛋白是多少？根据结果我需要复查吗？” | `MULTI_HOP` | 第二个问题依赖第一个问题的结果 |
| “如何修改患者处方并立即停药？” | `SAFE_BLOCK` | 命中安全策略 |

只有 `MULTI_QUERY` 才进入并行子问题检索；`SINGLE_QUERY` 继续使用现有链路；`MULTI_HOP` 按依赖顺序处理；`SAFE_BLOCK` 直接返回安全模板。路由结果、置信度和触发信号必须写入诊断信息，方便评测误拆分和漏拆分。

### 3.2 由测试确定的边界

路由边界先由 `tests/unit/test_query_router_boundaries.py` 固化，再作为实现和评测的契约：

| 输入特征 | 期望路由 | 处理方式 |
|---|---|---|
| 单个医学问题 | `SINGLE_QUERY` | 继续当前单查询链路 |
| 同一主题下询问多个正常范围/参考范围 | `SINGLE_QUERY` | 统一检索和回答，避免误拆分 |
| 两个以上独立疑问句 | `MULTI_QUERY` | 拆分后独立检索，检索阶段并行 |
| 编号列出的独立问题 | `MULTI_QUERY` | 按编号保留顺序后并行检索 |
| 后一个问题依赖前一个结果 | `MULTI_HOP` | 按依赖顺序执行，不强行并行 |
| 停药、改药或诊断类高风险请求 | `SAFE_BLOCK` | 直接使用安全模板 |

这些测试只验证路由，不声称知识库中存在某个医学事实。真实检索、引用和权限测试仍需使用项目已有知识库或经过确认的医学文档。

推荐链路：

```text
原始问题
  -> 原始安全分类
  -> QueryRouter
  -> 仅对 MULTI_QUERY 执行规则拆分 / LLM 兜底
  -> 子问题归一化与意图识别
  -> 受限并行子问题检索
  -> 子问题证据覆盖检查
  -> 结构化生成
  -> 子问题级引用校验
  -> 按原顺序汇总响应
```

## 4. 并行策略

拆分和排序是串行的；拆分完成后，各子问题检索相互独立，采用受限并发：

```text
拆分与排序
   ├─ Q1：归一化 -> 意图 -> 检索
   ├─ Q2：归一化 -> 意图 -> 检索
   └─ Q3：归一化 -> 意图 -> 检索
结果按 ordinal 恢复顺序
```

约束：

- 默认最大并发数为 4，不能无限制创建任务。
- 每个子问题有独立超时，整体请求仍受总超时限制。
- 一个子问题失败不能丢弃其他子问题的有效结果。
- 每个结果带 `sub_query_id`，不能只依赖返回列表位置。
- 共享 OpenSearch 客户端、连接池和 Embedding Cache。
- 有前置答案依赖的多跳问题按依赖顺序执行，不强行并行。

第一阶段采用“一次模型调用、结构化分段生成”，而不是立即为每个子问题单独调用模型，以控制延迟和成本。模型收到每个子问题及其专属证据，必须按 Q1、Q2、Q3 顺序回答；证据不足的问题单独输出无法可靠回答。后续评测证明一次生成不稳定时，再增加子问题分别生成后汇总的模式。

## 5. 数据契约

在 `medical_rag/query/contracts.py` 增加：

```python
@dataclass(frozen=True, slots=True)
class SubQuery:
    id: str
    ordinal: int
    text: str
    original_span: tuple[int, int] | None
    intent: Intent
    search_strategy: SearchStrategy
    split_confidence: float
```

扩展 `ProcessedQuery`：

```python
@dataclass(frozen=True, slots=True)
class ProcessedQuery:
    text: str
    original: str
    intent: Intent
    search_strategy: SearchStrategy
    sub_queries: tuple[SubQuery, ...] = ()
    used_llm: bool = False
    rewrite_log: tuple[str, ...] = ()
```

`sub_queries == ()` 表示兼容旧的单查询路径。单问题也可以生成一个 `SubQuery`，以便统一统计。

增加子问题结果契约：

```python
@dataclass(frozen=True, slots=True)
class SubQueryResult:
    sub_query_id: str
    ordinal: int
    status: Literal[
        "answered", "insufficient_evidence", "retrieval_unavailable",
        "timeout", "safety_blocked",
    ]
    normalized_text: str
    intent: Intent
    evidence: tuple[Evidence, ...]
    diagnostics: Mapping[str, object]
    reason: str | None = None
```

## 6. 详细流程

### 6.1 安全与拆分

1. 对原始问题执行现有安全分类；高风险请求直接走安全模板。
2. 使用规则生成候选片段，清理空片段、连接词和重复片段。
3. 对每个片段做归一化、上下文补全和意图识别。
4. 对边界不明确的输入调用受控 LLM；输出必须是结构化子问题列表。
5. 校验子问题非空、顺序稳定、覆盖原文关键内容，且不引入原文没有的医学事实。
6. 对拆分后的每个子问题二次执行安全分类。
7. 超过 6 个子问题时提示用户分批提问，防止上下文和延迟失控。

### 6.2 子问题检索

每个子问题构造独立 `SearchQuery`，使用自己的意图和 `SearchStrategy`，但复用同一个 `AccessContext`。私有检索仍严格限制在当前 tenant/patient；报告解释继续使用“私有优先、私有证据不足时补公共库”的现有策略。每个任务独立执行 BM25、向量检索、RRF、相关性门禁和父子上下文扩展。

### 6.3 证据合并和覆盖

结果返回后按 `ordinal` 恢复顺序。每个子问题内部去重证据；跨子问题只做展示层去重，不能把一个问题的证据重新归属给另一个问题。每个子问题分别计算是否有证据、是否通过门禁、是否有可定位引用、是否是检索故障。

`insufficient_evidence` 表示知识库证据不足；`retrieval_unavailable` 表示 OpenSearch、Embedding 或其他检索链路异常，两者必须区分。

### 6.4 生成和引用校验

提示词按以下结构组织：

```text
Q1：子问题文本
Q1 证据：...
Q1 状态：可回答/证据不足

Q2：子问题文本
Q2 证据：...
Q2 状态：可回答/证据不足
```

生成要求：保持原顺序、每段只回答对应问题、证据不足时明确说明、每个医学事实绑定可定位引用。引用校验器需要验证每个问题是否都有答案段、引用是否来自该问题证据集合、是否漏答、是否存在无证据医学断言。

## 7. 异常和降级

| 场景 | 处理 |
|---|---|
| 规则无法拆分 | LLM 兜底；仍失败则回退单查询 |
| 单个子问题超时 | 标记 `timeout`，其他问题继续 |
| OpenSearch 整体不可用 | 受影响问题标记 `retrieval_unavailable`，不生成无依据答案 |
| 单个问题证据不足 | 仅该问题返回证据不足说明 |
| 单个问题触发安全规则 | 阻断该问题；无法安全隔离时整条请求安全拒答 |
| 超过并发上限 | 排队执行，不创建无限任务 |
| 超过 6 个问题 | 提示用户拆分提问 |
| 模型漏答或引用错误 | 不展示未经校验的回答，返回安全降级 |
| 存在多跳依赖 | 按依赖图顺序执行 |

## 8. 可观测性

请求级记录 `multi_query_detected`、`sub_query_count`、`split_method`、`parallelism_used`、`total_latency_ms` 和最终状态。子问题级记录 `sub_query_id`、`ordinal`、`split_confidence`、检索耗时、证据数量、覆盖率、引用有效性、状态和失败原因。诊断中不能暴露患者正文、内部文档 ID 或跨租户信息。

## 9. 评测和上线门禁

评测集至少覆盖：并列指标、指标加健康教育、三个以上问题、私有和公共证据混合、单题证据不足、单题检索失败、高风险问题、口语和错别字、多跳依赖、提示注入混入普通医学问题。

核心指标：子问题拆分准确率和召回率；每个子问题的 Recall@K、MRR 和证据覆盖率；引用 validity、accuracy、coverage；完整回答率和部分失败隔离率；P50/P95 延迟、并发检索成功率；单问题回归通过率；跨患者、跨租户和 consent 泄露数（目标为 0）。

上线前必须满足：单问题回归不下降；子问题证据覆盖率达到既定阈值；引用 validity/accuracy 保持 1.0；安全隔离集无泄露；P95 不超过当前单问题预算的 1.5 倍；失败子问题不污染其他问题的证据集合。

## 10. 分阶段实施

1. **路由、契约和规则拆分**：增加 `query/router.py` 中的 `QueryRouter`、`QueryRoute`，以及 `SubQuery`、`SubQueryResult`、规则拆分器和单元测试。
2. **并行检索**：增加受限并发调度、子问题级超时、部分失败处理和诊断指标。
3. **生成与引用校验**：扩展结构化提示词，增加子问题答案段解析、漏答和跨题引用检查。
4. **复杂拆分和灰度**：接入受控 LLM 兜底，建立冻结评测集，完成灰度、性能测试和上线门禁。

## 11. 验收标准

1. 单问题行为兼容。
2. 两个独立问题生成两个有序答案段。
3. 独立检索任务支持受限并行。
4. 单个问题失败不会丢弃其他问题结果。
5. 每个答案段引用只能来自对应证据集合。
6. 证据不足和检索不可用可区分。
7. 无跨患者、跨租户或 consent 越权。
8. 拆分、检索、生成、校验均可追踪。
9. 多问题评测和单问题回归均通过门禁。
10. 异常场景不会展示未经验证的医学回答。
