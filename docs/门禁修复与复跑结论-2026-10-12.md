# 门禁修复与复跑结论（2026-10-12）

> 一句话结论：**无关查询拒答准确率 0.00 → 0.80**（30 条无关查询 0/30 → 24/30），
> 代价是相关查询 recall@3 0.9429 → 0.7571（相对 −19.7%）。安全项（越权/删除残留/
> 未审核泄漏）全程 `all_zero=True`。
>
> 证据：`eval_out/gate_rerun_v3/retrieval_eval_results.json`（真实 OpenSearch +
> 本地 ONNX，7 配置全跑，120 条用例）。

## 一、为什么上一轮复跑是无效的（根因链）

上一轮已经：定位到旧校准件阈值错、重新标定出 0.78、造好新校准件
`config/calibration/cosine-gate-2026-10-12.json`——**但漏了把 `.env` 的
`CALIBRATION_ARTIFACT_PATH` 从旧件切到新件**，于是那次 `gate_rerun_v2`
加载的仍是旧件，G1 拒答 = 0.00，结论无效。

完整因果链（这才是可复述的版本）：

| 环节 | 事实 | 后果 |
|---|---|---|
| 1 | 索引 `knn_vector` 映射为 `space_type=cosinesimil`（Lucene HNSW） | `_score = (1+cos)/2 ∈ [0.5, 1]` |
| 2 | 旧校准件声明 `score_space=l2_inv`、`cosine_threshold=0.50` | 阈值取自另一个分数空间 |
| 3 | 门禁实现是**逐候选裸比较**：`vector_score >= threshold`（`service.py:528`），`score_space` 只作元数据不做换算 | 0.50 恰好落在 cosinesimil 的下界 |
| 4 | `(1+cos)/2 ≥ 0.5` 恒成立 | **一个候选都砍不掉 → 永不拒答** |

验证：

```
$ python eval_out/_diag_gate.py     # 切 .env 前
artifact: cosine-gate-2026-09-26  cosine_threshold=0.5  score_space=l2_inv
gate_threshold=0.5   gate_policy=cosine_absolute
rejection case: rej-thyroid -> items=3   reason=None      # 未拒答

$ python eval_out/_diag_gate.py     # 切 .env 后
artifact: cosine-gate-2026-10-12  cosine_threshold=0.78  score_space=cosinesimil
gate_threshold=0.78  gate_policy=cosine_absolute
rejection case: rej-thyroid -> items=0   reason='insufficient_evidence'
```

**修复动作（配置层，未改任何代码）**：

1. `.env` 的 `CALIBRATION_ARTIFACT_PATH` → `config/calibration/cosine-gate-2026-10-12.json`；
2. 重写 `.env` 门禁注释块，写明「阈值必须在索引真实分数空间内标定」以及旧件为什么必然失效；
3. 备份 `.env.bak-2026-10-12`（`.env` 已被 gitignore，改动不进版本库）。

## 二、阈值标定依据（可复现）

`eval_out/_threshold_probe.py` 在真实索引上对 60 条相关 + 30 条无关查询做 top-1
分数扫描（判据等价性：候选按分数降序，「所有候选 < thr」⇔「top-1 < thr」）：

| 分布 | n | min | median | max |
|---|---|---|---|---|
| quality（相关） | 60 | 0.6714 | 0.8188 | 0.8876 |
| rejection（无关） | 30 | 0.7090 | 0.7506 | 0.8550 |

两组在 [0.709, 0.855] 区间**重叠但可分**。阈值扫描的平衡最优：

| thr | ≈cos | 拒答正确率 | 相关保留率 | min(两者) |
|---|---|---|---|---|
| 0.75 | 0.50 | 46.67% | 88.33% | 46.67% |
| 0.77 | 0.54 | 80.00% | 85.00% | 80.00% |
| **0.78** | **0.56** | **83.33%** | **83.33%** | **83.33%** |
| 0.79 | 0.58 | 83.33% | 76.67% | 76.67% |
| 0.80 | 0.60 | 83.33% | 68.33% | 68.33% |

选定 **0.78**（探针口径 83.3%/83.3%；端到端实测 0.80，差异来自门禁还要与词法
候选取交集）。

## 三、完整复跑结果（7 配置 × 120 用例）

命令：

```bash
python scripts/retrieval_tuning_lab.py --rounds 5 --out eval_out/gate_rerun_v3
```

`meta`：`calibration_artifact=cosine-gate-2026-10-12`；`corpus_integrity={public:30, private:8}`；
`category_counts={quality:70, rejection:30, safety:20}`。

| 配置 | recall@3 | MRR | nDCG@3 | top1 | **拒答准确率** | p95 (ms) | safety all_zero |
|---|---|---|---|---|---|---|---|
| A1 纯词法 | 0.9357 | 0.8048 | 0.8349 | 0.6857 | 0.00 (0/30) | 28.9 | ✅ |
| A2 纯向量 | 0.8571 | 0.7167 | 0.7530 | 0.5857 | 0.00 (0/30) | 185.0 | ✅ |
| A3 混合 rrf60 | 0.9429 | 0.8119 | 0.8470 | 0.6857 | 0.00 (0/30) | 2100.9 | ✅ |
| **G1 混合 rrf60 + 门禁** | 0.7571 | 0.6643 | 0.6895 | 0.5714 | **0.80 (24/30)** | 2096.8 | ✅ |
| B3 混合 rrf30 | 0.9429 | 0.8119 | 0.8470 | 0.6857 | 0.00 (0/30) | 2101.3 | ✅ |
| D2 混合 cand20 | 0.9429 | 0.8119 | 0.8470 | 0.6857 | 0.00 (0/30) | 2091.2 | ✅ |
| **G2 cand20 + 门禁** | 0.7571 | 0.6643 | 0.6895 | 0.5714 | **0.80 (24/30)** | 2094.7 | ✅ |

可直接引用的三条：

1. **拒答能力：0.00 → 0.80**（简历/面试主数字）。
2. **门禁代价可量化**：recall@3 −0.1858（相对 −19.7%）、MRR −0.1476、nDCG@3 −0.1575；
   拆解为「16.7% 相关查询被误拒（分数低于阈值）」+「约 2pt 的 gold 被挤出 top-3」。
   这正是相关性门禁的真实 trade-off，不要再宣称"零代价"。
3. **安全不变量**：7 配置 `safety.all_zero=True`（零越权、零删除残留、零未审核泄漏），
   门禁开启不破坏权限隔离。

次要观察（留作后续，不影响主结论）：

- A3 ≡ B3 ≡ D2：本语料（public 30 + private 8）下 `rrf_k` 30/60 与 `candidate_limit`
  20/50 **完全不敏感**——候选上限未触顶、融合序未变。样本量小，不可外推到大语料。
- G1 ≡ G2：同上。
- 混合档 p95 ≈ 2.1s，而纯向量档仅 185ms，**11 倍差异可疑**，疑与已知 P1-2
  （per-request 重建 ONNX）/ 混合路径预热有关，需单独定位；不要当成门禁的代价。

## 四、顺带发现：索引分数空间不可复现（建议立 spec）

修复过程暴露一个比"阈值错"更根本的问题：**现网索引的分数空间，代码里没有任何
一处声明它**。

| 位置 | 现状 | 问题 |
|---|---|---|
| 现网索引映射 | `space_type=cosinesimil`（lucene/hnsw） | 事实上的部署口径 |
| `retrieval/opensearch_writer.py:233` | `embedding: {"type":"knn_vector","dimension":N}`，**不声明 `space_type`** | 全新 `index-init` 会建出 **l2** 索引 |
| `retrieval/opensearch_store.py:27` | `VECTOR_SCORE_SPACE = "l2_inv"` | 与现网 cosinesimil 不符（注释自己写了"改 cosinesimil 须同步改常量并重建索引"） |
| `scripts/run_worker.py` | **磁盘上不存在** | `docker-compose.yml:126` 的 `index-init` 引用了它 → 索引**根本无法重建** |

后果：换一台机器从零部署，会得到 l2 索引 → 用 0.78（cosinesimil 口径）的门禁
→ 行为与本次验证结果不一致；把 `VECTOR_SCORE_SPACE` 当真的诊断消费者也会读到错标签。
`_assert_mapping_compatible` 只校验 `dimension` 与 `analyzer`，**不校验 `space_type`**，
不会拦住这种漂移。

建议按 `docs/superpowers/FEATURE-WORKFLOW.md` 走 spec → plan → TDD：

1. writer 映射显式声明 `space_type: cosinesimil` + `method{engine:lucene,name:hnsw}`；
2. `VECTOR_SCORE_SPACE` 改为 `cosinesimil`，并同步 `contracts.py` / `service.py` / `metrics.py`
   的相关注释；
3. `_assert_mapping_compatible` 增加 `space_type` 校验（不兼容即 fail-closed 并给重建指令）；
4. 补一条测试：对现网索引取 `get_mapping`，断言 `space_type` 与 `VECTOR_SCORE_SPACE` 一致；
5. 找回 / 重建 `scripts/run_worker.py`，让 `index-init` 可复现。

> 说明：本轮**未改动任何 `src/` 代码**——上述 1–3 属于生产代码变更，按项目纪律
> 需先过 spec 与 plan 的审批门禁。

## 五、口径与局限（务必随数字一起讲）

1. **gold 口径**：按规范 `gold_evidence_ids` 计指标，非历史 grouped（`gold_evidence_groups`）
   口径；故 recall 与历史 `accepted_hit_rate=1.0000` 不可直接比较。
2. **身份映射**为取证推断（public→租户 1111…1111；private→患者 2222…2222；
   safety→患者 B）；三类 `safety.all_zero=True` 与权限用例通过间接印证其正确。
3. **语料规模小**：public 30 + private 8 = 38 条。所有消融差异（rrf_k、candidate_limit）
   在此规模下不显著，结论不可外推。
4. **延迟口径**：每用例采样一次，`--rounds` 在本版 runner 仅作元数据，未真正重复采样；
   横向比较只在同一版 runner 内有效。
5. **未重建的脚本**：`scripts/retrieval_rejection_threshold_sweep.py`、
   `scripts/faithfulness_eval.py` 仍缺。
