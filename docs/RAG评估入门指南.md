# RAG 系统评估入门指南

> 面向对象：已能独立搭建 RAG 系统、但从未系统评估过的工程师
> 目标：建立一张可自己往下走的「评估地图」——知道评什么、怎么测、标准从哪来
> 日期：2026-09-19
> 与 `docs/RAG评估体系设计方案.md` 的关系：那份文档是本项目**落地版**（对接现有 `QualityGate` / `evaluate_retrieval` 等代码）；本文是**通用入门版**，补齐生成质量维度与工具选型，两者互补。

## 0. 先建立一个心智模型

### 0.1 为什么"搭完了"不等于"能上线"

RAG 系统有个隐蔽特性：**它几乎不会报错，但会安静地答错**。

传统软件的错误是显式的（500、异常、崩溃）；RAG 的错误是隐式的——检索召回了不相关文档，模型照着编了一段通顺但错误的话。没有评估，你只有"感觉还行"，而这在真实用户面前会迅速崩塌。

### 0.2 三层 + 一横切

RAG 的评估必须**分层**，因为同一个坏答案可能来自完全不同的环节，归因错了就改错了地方。

```
        ┌─────────────────────────────────────────┐
        │  横切层：工程与安全                       │
        │  延迟 · 成本 · 安全违规（零容忍）· 降级率   │
        └─────────────────────────────────────────┘
                          │ 贯穿全程
   ┌──────────────────────┴──────────────────────┐
   │  维度一 · 检索质量    「找到对的资料了吗」     │
   │  维度二 · 生成质量    「照着资料答对了吗」     │
   │  维度三 · 端到端质量  「用户最终满意吗」       │
   └─────────────────────────────────────────────┘
```

**一句话原则**：

> **检索决定上限，生成决定下限。**
> 检索没召回，再强的模型也答不对（上限被锁死）；检索召回了，模型仍可能幻觉（下限被拉低）。
> 所以**永远先评检索**——否则你会把检索的锅甩给模型，反复调 prompt 却毫无改善。

### 0.3 新手的第一个决策：有没有参考答案

这决定了你能用哪套指标，必须先想清楚：

| | 有参考答案（reference-based） | 无参考答案（reference-free） |
|---|---|---|
| 需要什么 | 每条 query 配一份标准答案 | 只需要 query + 检索上下文 + 系统答案 |
| 能测 | 准确率、召回、EM/F1、答案正确性 | 忠实度、相关性、上下文质量 |
| 成本 | 高（人工写答案） | 低（LLM 自评） |
| 适合 | 最终验收、回归门禁 | 日常迭代、冷启动 |

**新手的务实路线**：先做无参考答案（LLM-as-judge），等系统稳定了再补一个有参考答案的小而精的测试集做验收。

## 1. 评估维度总览

| 维度 | 回答什么问题 | 核心指标 | 主要方法 | 标注成本 |
|---|---|---|---|---|
| **一 · 检索质量** | 找到对的资料了吗？ | Hit@K、Recall@K、Precision@K、MRR、nDCG@K、Context Precision/Recall | 需 gold 证据标注 | 中 |
| **二 · 生成质量** | 照着资料答对了吗？ | Faithfulness、Answer Relevance、Context Relevance、Citation Accuracy | LLM-as-judge 为主 | 低 |
| **三 · 端到端质量** | 用户最终满意吗？ | 任务成功率、人工偏好胜率、用户反馈、拒答正确率 | 人工 + 线上反馈 | 高 |
| **横切 · 工程安全** | 快吗？贵吗？安全吗？ | P95 延迟、单次成本、安全违规数、降级率 | 纯自动采集 | 零 |

> **新手建议的评估顺序**：横切（零成本，立刻能做）→ 检索（决定上限）→ 生成（LLM 自评，成本低）→ 端到端（最后做验收）。

## 2. 维度一：检索质量

### 2.1 先理解"K"

`K` = 返回给模型的文档块数量（比如 top_k=5 就是取前 5 块）。**所有检索指标都带 K**，因为指标值强烈依赖 K——`Recall@20` 天然比 `Recall@5` 高。所以：

> **报告检索指标时，不写 K 的数值等于没报告。**

### 2.2 核心指标

设：`G` = 该 query 的相关文档集合（gold），`d₁…d_K` = 系统按排序返回的前 K 个，`N` = 评测 query 总数。

| 指标 | 公式 | 含义（直觉） | 它惩罚什么 |
|---|---|---|---|
| **Hit Rate@K**<br>命中率 | `HR@K = (1/N) Σ 1[∃ i≤K : dᵢ ∈ G]` | **"有没有找到"**——前 K 个里至少有一个对的就算命中 | 完全没召回（最严重） |
| **Recall@K**<br>召回率 | `Recall@K = (1/N) Σ \|{d₁…d_K} ∩ G\| / \|G\|` | **"找全了没"**——该找的找回来多少 | 漏掉相关文档 |
| **Precision@K**<br>查准率 | `Precision@K = (1/N) Σ \|{d₁…d_K} ∩ G\| / K` | **"混进来多少垃圾"**——返回的里有多少是相关的 | 塞无关内容占用上下文 |
| **MRR**<br>平均倒数排名 | `MRR = (1/N) Σ 1/rank₁`<br>`rank₁` = 第一个相关文档的位置 | **"第一个对的排多前"**——越靠前分越高 | 把好文档排在后面 |
| **nDCG@K** | `DCG@K = Σ (2^relᵢ−1)/log₂(i+1)`<br>`nDCG = DCG / IDCG` | **"整体排序对不对"**——考虑位置折扣的排序质量 | 排序整体错乱 |
| **MAP@K**<br>平均精度均值 | `AP = (1/\|G\|) Σ P@i × 1[dᵢ∈G]`<br>`MAP = mean(AP)` | **"相关文档的平均排名质量"**——综合位置与查准 | 相关文档分布靠后 |

**关系速记**：

```
Hit    = 有没有找到     （最宽松，第一个门槛）
Recall = 找全了没       （决定上限）
Precision = 有多干净    （决定信噪比）
MRR    = 第一个多靠前   （决定用户体验）
nDCG   = 排序整体多好   （最全面，推荐主指标）
```

### 2.3 RAG 专用的上下文指标（RAGAS 体系）

传统 IR 指标假设"相关/不相关"是二元的。RAG 场景还需要评**上下文本身的质量**：

| 指标 | 定义 | 直觉 |
|---|---|---|
| **Context Precision** | 检索到的上下文中，相关内容的**排名加权**占比 | 好的内容是不是排在前面 |
| **Context Recall** | 标准答案的每个信息点，能在检索上下文中找到依据的比例 | 资料够不够回答问题 |
| **Context Relevance** | 上下文与 query 的语义相关程度 | 资料跑题了没 |

> **Context Recall 与 Recall@K 的区别**：前者以**标准答案的信息点**为单位（答得出才算召回），后者以**文档**为单位。前者更贴近"能不能答对"。

### 2.4 怎么采集

1. **造评测集**：抽 `query` → 人工（或 LLM 辅助）标注 `gold_evidence_ids`（相关文档块 ID）。
2. **跑真实检索**：调用你的检索接口拿 Top-K 列表。
3. **比对计算**：按上表公式算，**务必显式指定 K**。
4. **分档报告**：按 query 类型（事实型/数值型/多跳型）和难度分层，整体均值会掩盖局部崩溃。

## 3. 维度二：生成质量（RAG Triad）

这是新手最容易忽略、但对 RAG 最关键的一层。业界有个很好用的框架叫 **RAG Triad（三元组）**——它把"生成好不好"拆成三个两两配对的关系：

```
              query
             ╱     ╲
   ① Context       ③ Answer
   Relevance       Relevance
           ╱         ╲
      context ─────── answer
            ② Groundedness
```

| 边 | 指标 | 回答的问题 | 低分意味着 |
|---|---|---|---|
| ① query ↔ context | **Context Relevance** | 检索的资料和问题相关吗？ | 检索跑题（问题在检索层） |
| ② context ↔ answer | **Groundedness / Faithfulness** | 答案有上下文依据吗？ | **幻觉**（模型编造） |
| ③ answer ↔ query | **Answer Relevance** | 答案真的回答了问题吗？ | 答非所问（跑题但没幻觉） |

**这个框架的价值**：三条边任一低分，你就知道该改哪一层——① 改检索，② 改 prompt/模型，③ 改 prompt。

### 3.1 生成质量指标表

| 指标 | 定义与计算 | 达标参考 | 标注 |
|---|---|---|---|
| **Faithfulness**<br>忠实度 | 答案中**能被上下文支持**的陈述数 / 答案总陈述数。由 LLM 把答案拆成原子陈述逐条核验 | ≥0.90（高风险）/ ≥0.80（一般） | LLM-as-judge |
| **幻觉率** | `1 − Faithfulness`（或：无依据陈述占比） | ≤5%（高风险）/ ≤10%（一般） | LLM-as-judge |
| **Answer Relevance**<br>答案相关性 | 由答案反向生成若干问题，与原问题算平均语义相似度 | ≥0.80 | LLM-as-judge |
| **Context Relevance** | LLM 判定上下文与 query 的相关程度（可给 0/1 或 1–5 分） | ≥0.70 | LLM-as-judge |
| **Answer Correctness** | 与标准答案的**事实 F1 + 语义相似度**加权组合 | ≥0.80 | 需参考答案 |
| **Citation Accuracy**<br>引用准确率 | 答案引用的来源**确实支持**该结论的比例 | ≥0.95 | LLM + 规则 |
| **Completeness**<br>完整性 | 标准答案的信息点被覆盖的比例 | ≥0.85 | 需参考答案 |
| **Noise Sensitivity**<br>噪声敏感度 | 上下文混入无关内容时，答案变错的比例 | ≤0.10 | 构造实验 |
| **Refusal Correctness**<br>拒答正确性 | 该拒答时拒答、不该拒答时作答的比例 | ≥0.95 | 需标注 |

### 3.2 一个必须建立的意识：拒答也是能力

医疗、金融等高风险场景，**"没有依据时说不确定"比"编一个答案"重要得多**。要专门构造两类 case：
- **应拒答**：知识库里确实没有答案 → 系统必须拒答或声明不确定
- **不应拒答**：知识库里有答案 → 系统不能过度保守

只测"答对了多少"会诱导系统过度自信。

## 4. 维度三：端到端质量

前两层是**分解诊断**，这一层是**最终验收**。指标少但更接近真实价值：

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **任务成功率** | 用户完成了原本想做的事的比例（如"查到了指标含义"） | 人工判定 / 埋点 |
| **人工偏好胜率** | 两版系统对同一 query，人工更偏好 A 的比例（A/B 对比） | 成对标注 |
| **用户反馈** | 点赞/点踩、追问率、转人工率、放弃率 | 线上埋点 |
| **答案采纳率** | 用户直接使用/复制答案的比例 | 线上埋点 |
| **拒答正确率** | 见 3.2 | 专项测试集 |

> **注意**：线上反馈有偏（不满意的用户直接走了，不留反馈），且易被"话术好听但内容错"欺骗。**线上信号用来发现异常，不用来证明正确**。

## 5. 横切层：工程与安全指标

这层**零标注成本**，新手应该第一天就接上：

| 指标 | 参考阈值 | 说明 |
|---|---|---|
| **端到端延迟 P50/P95/P99** | P95 ≤ 2s（交互式）/ ≤5s（可接受） | 分位比均值重要——用户记住的是最慢那次 |
| **分阶段延迟** | 检索 / 重排 / 生成各自 P95 | 定位瓶颈 |
| **单次查询成本** | 按业务定 | token 用量 × 单价，含检索与生成 |
| **安全违规数** | **必须为 0** | 越权访问、已删除数据残留、敏感信息泄漏 |
| **降级率 / 空返回率** | ≤2% | 检索不可用、无证据返回的比例 |
| **失败率** | ≤0.5% | 异常、超时 |

> **安全指标是零容忍项**：任何一个非零都直接阻断发布，**优先级高于所有质量指标**。因为质量差是"不好用"，安全违规是"不能用"。

## 6. 评估方法工具箱

### 6.1 三种方法对比

| 方法 | 成本 | 可扩展性 | 适合评什么 | 局限 |
|---|---|---|---|---|
| **人工评估** | 高 | 低 | 主观质量、最终验收、校准其他方法 | 慢、贵、标注者间不一致 |
| **自动规则** | 零 | 极高 | 延迟、成本、安全、精确匹配、引用格式 | 无法评语义质量 |
| **LLM-as-judge** | 低 | 高 | 忠实度、相关性、上下文质量 | 有偏差，需校准 |

**推荐组合**：自动规则做兜底（安全+工程）→ LLM-as-judge 做日常迭代 → 人工做验收和校准。

### 6.2 LLM-as-judge 的四个坑（必读）

这是新手最容易踩的地方：

| 坑 | 表现 | 对策 |
|---|---|---|
| **位置偏差** | 成对比较时偏好第一个 | 交换顺序各评一次，取一致结果 |
| **冗长偏差** | 偏好更长的答案 | 控制长度，或显式提示"长度不是质量" |
| **自我偏好** | 偏好与自己同源的模型输出 | judge 与被评模型尽量不同源 |
| **分数坍缩** | 永远给 4/5 分 | 用二元判断或强制分布，定期人工校准 |

**校准是硬要求**：人工标注 50–100 条作为金标，计算 judge 与人工的 **Cohen's kappa**：

- `kappa ≥ 0.70` → 可用于自动评测
- `0.40 ≤ kappa < 0.70` → 只能做趋势参考，不能做门禁
- `kappa < 0.40` → 不可用，需改 prompt 或换模型

### 6.3 常用开源工具

| 工具 | 定位 | 特点 | 适合 |
|---|---|---|---|
| **RAGAS** | RAG 专用评估库 | reference-free 指标齐全（faithfulness / answer relevancy / context precision / context recall）；自带合成测试集生成 | **新手首选**，与 RAG 场景最贴合 |
| **TruLens** | 可观测 + 评估 | 提出 RAG Triad 框架，反馈函数可视化 | 想理解三元组概念 |
| **DeepEval** | pytest 风格评估 | 14+ 指标，可像写单测一样写评估，易进 CI | 想接 CI 门禁 |
| **ARES** | 自动化评估框架 | LLM judge + 统计置信区间（PPI），学术严谨 | 需要置信度报告 |
| **Arize Phoenix** | 可观测平台 | 链路追踪 + 内置评估，可视化强 | 需要 debug 检索链路 |
| **Langfuse / LangSmith** | 可观测 + 评测 | 线上 trace、数据集管理、A/B | 需要线上监控闭环 |
| **promptfoo** | 回归测试 | 配置驱动，适合 prompt 版本对比 | prompt 迭代快 |

**新手路线建议**：**RAGAS 起步**（概念最贴合、上手最快）→ 需要进 CI 时加 **DeepEval** → 需要线上监控时加 **Langfuse**。

### 6.4 有参考答案 vs 无参考答案怎么选

| 场景 | 选择 |
|---|---|
| 系统刚搭好，还没标注 | **无参考答案**：RAGAS 的 faithfulness + answer relevancy + context relevance |
| 准备上线验收 | **有参考答案**：造 100–200 条金标，测 Answer Correctness + Completeness |
| 日常迭代防退化 | **回归基线**：冻结上一版指标值，只看有没有变差 |
| 高风险场景（医疗/金融） | **两者都要** + 安全零容忍 + 拒答专项 |

## 7. 如何设定基准与判断标准

### 7.1 新手最大的误区

> **误区：一上来就去找"业界标准阈值"。**

真相是：**不存在通用的绝对阈值**。原因有三：

1. **领域差异巨大**——医疗要求的忠实度远高于闲聊机器人。
2. **K 值不同不可比**——`Recall@5 = 0.7` 和 `Recall@20 = 0.7` 完全是两回事。
3. **数据分布不同**——你的 query 难度分布决定了一切。

**正确的思路**：阈值不是"查来的"，是**测出来 + 校准出来的**。下面给方法。

### 7.2 三种基准类型（按可靠性排序）

| 类型 | 怎么定 | 什么时候用 | 可靠性 |
|---|---|---|---|
| **相对基线**<br>Regression Baseline | 冻结当前版本指标值，只要求新版本不劣化 | **冷启动首选**，第一天就能用 | 高（但可能一开始就很低） |
| **分档阈值**<br>Tiered Threshold | 按难度/类型分别设阈值（易题要 0.95，难题 0.6） | 数据够分层时 | 高 |
| **绝对阈值**<br>Absolute Target | 业务方认可的硬指标 | 有足够数据和业务共识后 | 中（易过时） |

**建议组合**：`绝对阈值（安全项，零容忍）` + `相对基线（质量项，防退化）` + `分档阈值（诊断项，定位问题）`。

### 7.3 阈值校准四步法

```
① 测量      用 50–100 条评测集跑出当前真实指标值
                │
② 看分布    不只看均值，看 P10/P50/P90 —— 尾部才是问题所在
                │
③ 定基线    取"当前中位数 − 合理缓冲"，作为回归门禁
            （例如 faithfulness 当前 0.82 → 门禁设 0.80）
                │
④ 逐步收紧  每解决一批 bad case 后重测，把阈值往上推，
            直到接近人工判断的"可接受线"
```

**关键**：第 ④ 步的终点不是"越高越好"，而是**与人工判断对齐**。指标高但人工觉得差，说明指标选错了。

### 7.4 起点参考区间（务必用你自己的数据校准）

以下是常见开源项目与实践中观察到的**量级参考**，仅用于判断"你的数字是不是离谱"，**不能直接当阈值**：

| 指标 | 一般可用 | 较好 | 高风险场景要求 |
|---|---|---|---|
| Recall@10 | 0.70–0.85 | ≥0.90 | ≥0.95 |
| Precision@5 | 0.40–0.60 | ≥0.70 | ≥0.80 |
| MRR | 0.55–0.70 | ≥0.80 | ≥0.85 |
| nDCG@10 | 0.55–0.70 | ≥0.80 | ≥0.85 |
| Faithfulness | 0.70–0.85 | ≥0.90 | ≥0.95 |
| Answer Relevance | 0.70–0.85 | ≥0.85 | ≥0.90 |
| Context Relevance | 0.50–0.70 | ≥0.75 | ≥0.85 |
| Citation Accuracy | 0.80–0.90 | ≥0.95 | ≥0.98 |
| 幻觉率 | 10–20% | ≤5% | ≤2% |
| P95 延迟 | ≤3s | ≤1.5s | ≤1s |

> **如何自检阈值是否合理**：如果某个指标长期是 1.00 或 0.00，几乎可以肯定**测法有问题**（测试集太简单、或指标口径错误），而不是系统完美或崩溃。真实系统的指标应该落在中间区间且有波动。

### 7.5 判断标准的三种"硬度"

不同指标该用不同的判断逻辑，混用会导致误判：

| 硬度 | 逻辑 | 适用 | 例子 |
|---|---|---|---|
| **零容忍** | 非零即失败，无条件阻断 | 安全、合规 | 越权访问、敏感信息泄漏、删除数据残留 |
| **回归门禁** | 不得低于已冻结基线（容忍噪声） | 质量指标 | 忠实度、召回率 |
| **绝对目标** | 达到某数值才算通过 | 交付验收 | 任务成功率 ≥85% |

**噪声容忍**：延迟这类墙钟指标天然抖动，门禁应容忍合理倍数（如 2–3×）而非精确相等，否则会被时钟噪声反复误报。

### 7.5 样本量怎么定

| 用途 | 样本量 | 说明 |
|---|---|---|
| 冒烟测试 / 快速迭代 | 20–50 条 | 能发现大问题，不能做统计结论 |
| 稳定评测 / 回归门禁 | 100–300 条 | 指标波动可接受，推荐起步规模 |
| 上线验收 | 300–500 条 | 分层覆盖各类型与难度 |
| A/B 显著性判断 | 每侧 ≥200 条 | 小样本差异可能只是噪声 |

**分层原则**：宁要 100 条覆盖 5 种类型的，不要 500 条全是同一类型。**均值会骗人**——整体 0.85 可能是易题 0.98 + 难题 0.30 平均出来的。

## 8. 新手两周启动计划

| 阶段 | 做什么 | 产出 |
|---|---|---|
| **第 1–2 天** | 接工程与安全埋点（延迟、成本、安全违规） | 零成本监控看板 |
| **第 3–5 天** | 抽 50 条真实 query，人工标注 gold 证据 | 第一个检索评测集 |
| **第 6–8 天** | 跑检索指标，**显式指定 K**，分档报告 | 检索基线（含 P10/P90） |
| **第 9–11 天** | 接入 RAGAS，跑 faithfulness / answer relevance / context relevance | 生成质量基线 |
| **第 12–13 天** | 人工标注 50 条，算 LLM-judge 的 kappa | judge 可信度结论 |
| **第 14 天** | 用"中位数 − 缓冲"设回归门禁，接进 CI | 第一版自动门禁 |

**完成后的状态**：你有了**真实基线**（不是构造出来的满分）、**可自动回归的门禁**、**能定位问题的分层指标**。之后就是持续扩大评测集、逐步收紧阈值。

## 10. 一句话总结

> **分层评、先检索、用 LLM 自评起步、用人工校准 judge、用相对基线设门禁、用安全项兜底。**
> 阈值不是查来的，是测出来并对齐人工判断的；评测集不是越全越好，是分层覆盖 + 持续扩充。
