## 一、致命问题（P0，必须修复）

### P0-1【新发现】`space_type` 契约断裂：写入器不声明分数空间，导致新部署全拒答、现网部署不可复现

**位置**：

- 写入侧：`src/medical_rag/retrieval/opensearch_writer.py:252`
- 读取侧：`src/medical_rag/retrieval/opensearch_store.py:122-125`
- 判定侧：`src/medical_rag/retrieval/service.py:537-563`
- 组装侧：`src/medical_rag/api/composition.py:76`（构造 `OpenSearchStore` 时**未传** `vector_score_space`）

**证据链**（三方交叉验证，非单点推断）：

1. writer 建索引时 embedding 字段只声明维度：

```python
# opensearch_writer.py:252
"embedding": {"type": "knn_vector", "dimension": self.embedding_dimension},
```

全仓 `grep -rn "space_type" src/ scripts/` 无任何写入路径声明它。

1. store 的 resolver **只认显式声明**，缺失即返回 `mapping_unavailable`：

```python
# opensearch_store.py:122-125
space_type = method.get("space_type") if isinstance(method, dict) else None
if space_type not in _SCORE_SPACES:
    return MAPPING_UNAVAILABLE
```

1. 校准工件（`.env` 指向 `config/calibration/cosine-gate-2026-10-12.json`）声明 `score_space: "cosinesimil"`，而 `service.py:544` 要求物理 mapping 与之一致，不一致即 fail-closed 返回空结果 + `calibration_artifact_mismatch`。

**影响**：用 `init-indexes` 全新建索引（无 `space_type`）+ 按现网 `.env` 配置门禁 → **每一条查询都返回空集，聊天接口永远回答「检索服务暂时不可用」**。当前现网能用，说明线上索引的 mapping 是**带外手工创建**的——仓库无法复现自己的部署（10-12 报告已注明「索引分数空间不可复现……未修复/待立项」，本次确认仍未修复且升级为系统性风险）。

**修复建议**：

```python
# opensearch_writer.py —— 构造函数增加 space_type 参数（默认与校准工件对齐）
def __init__(self, ..., space_type: str = "cosinesimil") -> None:
    if space_type not in {"l2_inv", "cosinesimil"}:
        raise ValueError("space_type must be l2_inv or cosinesimil")
    self.space_type = space_type

# ensure_mapping 的 body 中：
"embedding": {
    "type": "knn_vector",
    "dimension": self.embedding_dimension,
    "method": {"name": "hnsw", "space_type": self.space_type},
},
```

同时在 `_assert_mapping_compatible`（opensearch_writer.py:149-188）中增加 `space_type` 冲突检查，并在 `composition.py` / `scripts/run_worker.py` 组装处透传。修复后需重建索引（`space_type` 建后不可改）。

**验证方式**：新增契约测试——用真实 OpenSearch 容器跑 `init-indexes` → 断言 `get_mapping` 中 `embedding.method.space_type == artifact.score_space` → 再跑一条真实检索断言非空。

### P0-3（10-13 P0-1 确认未修复）公共知识 ingest 在 DB commit 前写外部索引——幽灵索引记录

**位置**：`src/medical_rag/knowledge/ingest_service.py:300 → 308`

**原代码**：


**影响**：commit 失败（连接闪断、约束冲突）→ 索引已有记录而 DB 已回滚 → 检索命中无 DB 背书的幽灵 chunk；反向顺序则产生 DB 有、索引无的「静默不可见」。`_index_batch` 内 bulk 部分失败时异常上抛，同样留下半写状态。私有索引链路已用 Outbox 模式（`indexing/outbox.py`，事务性、载荷仅标识符+哈希）解决同一问题——**公共路径绕开了自家已验证的架构**，属于架构一致性铁律（半迁移状态）违例。`reconciliation.py` 只能事后发现，不能消除窗口。

**修复建议**：公共知识 ingest 改走与私有链路相同的 Outbox 事件（`knowledge.source_ingested` 提交于同一事务，worker 消费后写索引）；过渡期最小改动是把 `session.commit()` 移到 `_index_batch` 之前，并为 `_index_batch` 失败补补偿性删除（按 `content_hash` 批次回滚）。

### P1-3 查询归一化无词边界子串替换——英文缩写反例已可复现

**位置**：`src/medical_rag/query/normalize.py:29-31`

**原代码**：

```python
for term, standard in TERM_MAP.items():
    normalized = normalized.replace(term, standard)
```

**反例**（证伪门禁通过）：患者输入「ACTH 是什么」（促肾上腺皮质激素）→ `CT` 无边界匹配 → 输出「A计算机断层扫描CTH是什么」，检索词被系统性破坏。中文条目（如「脖子疼」）无此问题，风险集中在 `CT`、`Hb` 两个拉丁条目。

**修复建议**：拉丁词条用 `re.sub(rf"(?<![A-Za-z]){re.escape(term)}(?![A-Za-z])", standard, text)`；或仅对 `len(term) >= 2` 的中文词条保留 `replace`。

## 四、正向评价（做得好的地方）


这份代码库在后端核心上的工程素养**明显高于同规模试点项目的平均水平**：

1. **分数空间意识**：`l2_inv` vs `cosinesimil` 陷阱（`service.py:106-140` 注释「0.5 在两个空间恰好数值相同」）在业界是高频翻车点，本项目不仅识别还做了成对声明 + fail-fast。
2. **fail-closed 文化的一致性**：非开发环境 lifespan 拒绝半接线启动（`app.py:46-48`）、降级索引在就绪探针里如实上报、`retrieval_unavailable` 与 `insufficient_evidence` 的语义区分（`service.py:766-784`）、「集群宕机不能被说成没有医学证据」——这是对的患者安全设计。
3. **门禁自检放在 try/except 之外**（`app.py:94-97` 注释解释了为什么放里面会被吞）——对异常边界的理解到位。
4. **测试设计有证伪意识**：拒答门禁测试含「关闭门禁会返回不相关候选」的变异对照（`test_rejection_gate.py`），这不是形式化测试。
