## 1. 交付内容

### 1.1 恢复测试绿（承前）

`tests/integration/test_public_knowledge_retrieval_loop.py` 中那条**钉住旧缺陷**的测试已断言修复后的行为。原状态 `1 failed, 662 passed` 的成因：2026-09-18 13:29–13:30 给 `InMemorySearchIndex` 补了 `delete_record`、给 `ReconciliationService` 加了 writer 拆分，但该测试未同步。

拆成两条，各钉一件事：

- `test_registry_deactivation_leaves_a_residual_that_only_reconciliation_repairs`：领域层的 `set_active` 不碰索引（有意分层），因此任何绕过运维命令的生命周期变更都会留下残留——这是对账必须存在且必须可运行的理由。
- `test_reconciliation_removes_the_deactivation_residual`：残留可被删除，且 `repair` 成功。

### 1.2 停用/启用与公共索引同步

- `KnowledgeIngestService.reindex_source(source_id)`（新增）：从库中 `active` 的分块重建公共索引记录，复用 `ingest` 的版本指纹与 embedding 通道；`location` 严格取自存储列（不额外回退 `section`），以免"重新启用"比"新鲜入库"更可检索这种不对称。
- `knowledge-set-active`（`scripts/run_worker.py`）：停用时**物理删除**该源全部分块的索引记录；启用时调用 `reindex_source` 写回。**先提交数据库、再动索引**：索引残留可被对账发现并修复，而"索引已删但事务回滚"会造成无扫描器可见的静默内容丢失。
- 索引侧失败时**非零退出 + 明确文案**，绝不打印成功。

### 1.3 `knowledge-reconcile` 运维入口

`ReconciliationService` 此前在 `src/` 下的构造点为 **0**（仅测试）。新增命令：

```
python scripts/run_worker.py knowledge-reconcile [--scope public] [--limit 100] [--apply]
```

默认仅扫描；`--apply` 才修复。退出码：`0` 干净 / `1` 有残留或仍有未修复项 / `2` 无法观测索引。

接线按 `ReconciliationService` 的 writer 拆分：枚举走 `OpenSearchStore`（读别名），删除走 `OpenSearchIndexWriter`（物理索引）。

### 1.4 `OpenSearchStore.scan(scope, limit)`（新增能力）

对账的"观察侧"原本不存在：写路径持有物理索引名，读路径只知道别名，两个适配器都无法列出自己的内容——`ReconciliationService.__init__` 里"`OpenSearchStore` 能枚举但不能删"的注释与实际代码不符。新增的枚举接口只取身份元数据（**不含 `text`**），查询读别名，返回带 `id`（取自 `_id`）的映射。

### 1.5 分析器显式回退（超出批准范围，见 §3）

`_writers()` 此前未把 analyzer 传给 writer，默认 `ik_max_word`/`ik_smart`。本机集群**未安装 analysis-ik 插件**，导致 `ensure_mapping` 直接 400、**一条知识都写不进去**（见 §2 证据）。新增 `RAG_TEXT_ANALYZER` / `RAG_SEARCH_ANALYZER` 环境变量：

- 不设置 → 保持 writer 默认（`ik_max_word` / `ik_smart`），行为不变；
- `cjk` → 使用内置二元分析器；
- `none` / `default` → 显式接受 OpenSearch 默认。

回退必须显式配置，与 writer 既有注释一致（"不允许静默降级"）。

### 2.2 真实链路（真集群 + 隔离数据库）

用**真实 OpenSearch 集群**（`http://localhost:9200`，索引与别名齐备）跑通完整生命周期，数据库用 `medical_rag.db` 的**副本**，不触碰原库：

```
live public index documents (before): 0
knowledge-register（启用 + 审核人）        exit=0
knowledge-list                            exit=0   块 0/0 活跃
knowledge-ingest（2 段正文）              exit=0   入库完成: 新增 2 块，跳过 0 块，写入索引 2 块
knowledge-reconcile --scope public        exit=0   scanned=4 residuals=0
knowledge-set-active --inactive           exit=0   已从公共索引删除 2 块
knowledge-reconcile --scope public        exit=0   scanned=2 residuals=0
knowledge-set-active --active             exit=0   已写回公共索引 2/2 块
knowledge-reconcile --scope public        exit=0   scanned=4 residuals=0
knowledge-set-active --inactive（收尾）    exit=0   已从公共索引删除 2 块
```

刷新后核对真实索引：**公共索引文档数为 0**，无联调残留（联调写入的文档已由收尾的停用删除）。

> 说明：驱动脚本里的 `_count` 在命令后立即读取，受 OpenSearch 默认 1s refresh 影响会滞后一步，因此脚本中"after ingest: 0 / after deactivate: 2"这类计数是**读数假象**；以刷新后的核对为准。命令自身的输出（写入 2 块 / 删除 2 块）与最终索引状态一致。

### 2.3 失败路径（真环境）

| 场景 | 结果 |
|---|---|
| 集群不可达（`OPENSEARCH_URL` 指向关闭端口） | 修复前：未捕获的 `ConnectionError` 堆栈 + 退出 1（会被读成"发现残留"）；修复后：`exit=2` + "无法观测 public 索引，未给出判定"，无堆栈 |

## 3. 偏差上报

### 3.1 超出批准范围：分析器环境变量（§1.5）

用户批准的是"1（恢复绿）+ 2（停用生效 + 对账入口）"。`_writers()` 未透传 analyzer 是本机集群**完全无法入库**的硬阻塞（`analyzer [ik_smart] has not been configured in mappings`），不修则真实链路无法验证、交付物在真机上不可用。改动不改默认值，仅增加显式配置入口。**恢复条件**：集群安装 `opensearch-analysis-ik` 后，可移除这两个环境变量的设置，回落到 `ik_max_word`/`ik_smart`。

### 3.2 修复了一处真实缺陷：读模型/写模型身份字段不对称

`ReconciliationService._metadata` 只读顶层 `source_id`/`source_version`，而读模型 `SearchRecord` 把公共来源身份放在 `citation` 里 —— 于是观察侧这两个字段恒为 `None`，`_reason` 的 stale 比较会把**每一条健康公共记录判为 `stale`**，action 为 `rebuild`；public 的 rebuild 又必然 `rebuild_required`，扫描将永久报红且修不掉（训练运维忽略告警）。

修复：`_metadata` 在顶层缺失时从 `citation` 回读。**影响范围界定**：新建的 `OpenSearchStore.scan` 返回原始 `_source`（含写入器写下的这两个字段），故真实部署路径本不受影响；受影响的是以 `SearchRecord` 作为观察侧的适配器。既有测试未发现该缺陷，原因是它用记录型 writer 返回 `IndexRecord`（字段齐全），比真实适配器"更富"。

### 3.3 环境限制

- 本机集群**无 analysis-ik 插件**，且现有 `medical-rag-public-local` 的 `text` 字段映射为 `{type: text}`（无分析器）。因此联调使用 `RAG_TEXT_ANALYZER=none` 显式接受默认分析器——`cjk` 或 `ik_max_word` 都会因"无法修改既有字段的分析器"而被拒绝。**要获得中文词级检索质量**，需重建索引并在支持插件的集群上启用 `ik_max_word`，或显式配置 `cjk`。
- `OpenSearchStore.scan` 仅用假客户端做了契约验证，未在真实集群上跑过端到端扫描路径（真实集群的 `_count`/`search` 已单独核对，但 `scan` 的完整调用链属本次新代码）。**恢复条件**：`RAG_LIVE_OPENSEARCH=1` 的实盘测试补一条 `scan` 断言。
- 本次未验证"停用后患者端检索为空"的**API 层**表现（属读路径，且需要启动完整服务与鉴权上下文）；已在服务层用 `RetrievalService` 断言（`test_deactivate_then_retrieve_returns_nothing`、`test_reactivate_then_retrieve_returns_the_evidence_again`）。
