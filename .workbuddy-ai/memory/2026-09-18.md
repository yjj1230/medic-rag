### 做法：`InMemorySearchIndex` 同时充当写接缝与读接缝

全链路可在内存内闭合，**零新增生产代码、零基础设施**：

- `KnowledgeIngestService._index_batch` 会 dispatch 到带 `upsert` 的 sink
  （`ingest_service.py:182-187`）；
- `RetrievalService` 因为该索引**没有** `search_lexical` / `search_vector`
  而走 legacy 单路分支（`service.py:197-199`），因此不需要 `HybridRanker`、
  embedding 或标定件。

`InMemorySearchIndex` 是代码库中唯一同时满足两套接缝的对象（`upsert` +
`search`/`search_by_parent`），所以一个实例即可当 sink 又可当 source。
它此前只在 5 个测试里当**读**索引用过，从未当写入目标。

### 本轮查实的四个坑（写这类测试极易写「假绿」）

1. **`_has_citation` 要求 location 非空**（`service.py:156-158`）。
   `KnowledgeChunkDraft.from_evidence` 取 `location = source.location or section`
   （`knowledge/contracts.py:175`）。
   - 有 markdown 标题 → `section_path[-1]` 兜底，**可召回**；
   - 平铺正文且不传 `--location` → `location=None` → 记录写进去了、
     `indexed_chunks` 也 +1、CLI 打印成功，**但永远检索不到**。
   （原以为会走「完全不可召回」，实测才发现标题兜底这条路是通的，
   原来的用例断言写错了，已拆成两个方向分别固化。）
2. **`InMemorySearchIndex.search` 按空白切词**（`contracts.py:403`），
   纯中文查询拿不到 lexical 加成（<=0.2）。断言不能依赖中文词命中。
3. **`ReconciliationService._reason` 对两侧任一为 `None` 的字段直接跳过**
   （`reconciliation.py:299-308`）。若索引里放的是 `SearchRecord`
   （无 `content_hash`/`parser_version`/`index_version`），对账断言会**空转**，
   必须 upsert 真正的 `IndexRecord` 并断言 `item.observed`。
4. **本仓 `.env` 会泄漏真端点**，测试必须
   `Settings(_env_file=None, environment="test", model_gateway_model_api_key=None)`
   \+ `delenv RAG_ALLOW_UNEMBEDDED / RAG_BM25_ONLY`。

### 新发现的两个生产缺口（已在测试里就地固化，未修）

- **P0｜公共侧的对账删除根本走不通。**
  `set_active(False)` 只改 DB 行、不动索引（`ingest_service.py:85-112`），
  索引条目仍是 `retrieval_eligible=True/source_active=True`，
  所以**停用后内容继续被检索返回**，必须靠对账删残留。
  但 `ReconciliationService._delete`（`reconciliation.py:447-465`）只在
  `delete_record` / `delete_id` / `delete` / `delete_document` 里找接缝，
  而公共索引侧唯一接上的 `OpenSearchStore` **这四个都没有**
  （实测 `InMemorySearchIndex` 也一个都没有）。
  → 停用知识源会产生「扫描能发现、却永远修不掉」的残留。
  私有侧有 `InMemoryPrivateIndexWriter.delete_record`，所以覆盖完整；
  **公共侧完全没有覆盖**（`test_index_reconciliation` 只断言了 reason 和事件）。
  真实部署要修：给 `OpenSearchStore` 加 `delete_record` 并在
  `run_worker` 里接上，或让 repair 直接复用 writer。
- **P1｜`PublicIndexRecord.to_index_record()` 丢字段。**
  `knowledge/contracts.py:238-266` 不转发
  `parent_block_id` / `chunk_index` / `section_path` / `quality_flags` /
  `raw_text` / `clean_text`。而 `semantic_chunker` 在**超长块切分**和**表格块**
  上会设 `parent_block_id`（`semantic_chunker.py:253/322/342`）。
  → 公共知识的父子块上下文扩展（Task 9）在链路上**不可能生效**，
  因为链接在 chunker→index 之间就断了。比之前记录的
  「父子块覆盖面比文档描述的窄」更严重。
